# Security Policy

GreenKube holds credentials that can write to your Git repositories and reads
cluster-wide inventory. We treat security reports as the highest priority.

## Supported versions

| Version | Supported |
| --- | --- |
| Latest minor release (currently 0.3.x) | Security fixes |
| `dev` branch and `dev-*` images | Fixed on `dev`, released with the next version |
| Older minor releases | No; upgrade to the latest release |

## Reporting a vulnerability

**Do not open a public issue, discussion or pull request for a vulnerability.**

1. Preferred: use GitHub's private vulnerability reporting, **Security → Report a
   vulnerability** on <https://github.com/GreenKubeCloud/GreenKube/security/advisories/new>.
2. Or e-mail the maintainer at **hugo.lelievre@greenkube.cloud** with "GreenKube security"
   in the subject.

Please include the affected version or commit, the component (api, controller,
renderer, worker, Helm chart, UI), the configuration needed to reproduce, the
impact you observed and, if you have one, a proof of concept. Never include real
tokens or customer data.

What to expect:

- an acknowledgement within **3 working days**;
- a first assessment (confirmed, needs information, or not a vulnerability) within **10 working days**;
- a fix or mitigation plan agreed with you, a GitHub Security Advisory and a CVE
  when relevant, and credit in the advisory unless you prefer to stay anonymous.

Please give us a reasonable time to release a fix (90 days by default) before
any public disclosure.

## Scope

Especially in scope:

- anything that lets GreenKube change a workload **outside Git**, or write to a
  repository, branch or file the policy does not allow (principle: Git is the
  only write path);
- leakage of Git provider tokens, GitHub App keys, API keys, session cookies or
  database credentials (logs, API responses, metrics, PR bodies, the UI);
- escaping the isolated renderer (Helm/Kustomize rendering of untrusted repositories);
- authentication, session, CSRF and authorization bypasses on the API;
- tampering with the savings ledger that its hash-chain verification does not detect;
- the Helm chart granting more RBAC or pod privileges than documented.

Out of scope: findings that need cluster-admin or write access to the GreenKube
namespace already, denial of service by an authenticated administrator, and
vulnerabilities in third-party images with no GreenKube-specific impact (report
them upstream; we track them with Trivy in CI).

## Hardening

The threat model (trust boundaries, roles and scopes per route group, credentials,
renderer isolation, outbound requests, residual risks) and a production
hardening checklist are in [Security model](docs/security-model.md).

- Every pod of the chart meets Pod Security `restricted` by default; see
  [Installation → Pod Security Admission](docs/installation.md#pod-security-admission).
- The bundled PostgreSQL accepts connections from GreenKube's own components only
  (`postgres.networkPolicy`, on by default). Enable `monitoring.networkPolicy.enabled`
  to restrict ingress and egress of the other components.
- Serve the UI over HTTPS (see [Installation → Ingress and TLS](docs/installation.md#optional-ingress-and-tls)),
  set `config.trustedProxyIps` to your Ingress controller addresses, and use scoped
  API keys and accounts ([Authentication](docs/authentication.md)). Upgraded installs:
  retire the deprecated bootstrap key (`auth.legacyApiKey`).
- CI runs CodeQL, Trivy and `npm audit` on every change.

## Verifying releases

Release images and chart packages are built by `.github/workflows/release.yml`
from a version tag, with every GitHub Action pinned by commit SHA. Releases
built by this workflow since the supply-chain hardening (roadmap O6) carry:

- a **cosign keyless signature** of the image (Sigstore, GitHub OIDC identity);
- an **SPDX SBOM** generated by syft, attached to the image as a signed
  attestation and to the GitHub Release as `greenkube-<version>.spdx.json`;
- **SLSA build provenance** (GitHub artifact attestations) for the image and the
  chart package, plus BuildKit provenance and SBOM in the image index;
- a Sigstore bundle for the chart package (`greenkube-<version>.tgz.sigstore.json`).

Verify the image signature and SBOM attestation:

```bash
VERSION=0.4.0   # the release you install
IDENTITY='^https://github.com/GreenKubeCloud/GreenKube/.github/workflows/release.yml@refs/tags/v'
ISSUER=https://token.actions.githubusercontent.com

cosign verify "greenkube/greenkube:${VERSION}" \
  --certificate-identity-regexp "${IDENTITY}" --certificate-oidc-issuer "${ISSUER}"

cosign verify-attestation --type spdxjson "greenkube/greenkube:${VERSION}" \
  --certificate-identity-regexp "${IDENTITY}" --certificate-oidc-issuer "${ISSUER}"
```

Verify the build provenance (GitHub CLI 2.49 or later):

```bash
gh attestation verify "oci://index.docker.io/greenkube/greenkube:${VERSION}" --repo GreenKubeCloud/GreenKube
gh attestation verify "greenkube-${VERSION}.tgz" --repo GreenKubeCloud/GreenKube
```

Verify the chart package downloaded from the Helm repository or the GitHub Release:

```bash
cosign verify-blob "greenkube-${VERSION}.tgz" \
  --bundle "greenkube-${VERSION}.tgz.sigstore.json" \
  --certificate-identity-regexp "${IDENTITY}" --certificate-oidc-issuer "${ISSUER}"
```

Pin the image by the digest printed in the release notes with the chart value
`image.digest: sha256:<digest>`, and enforce signatures at admission with a
policy engine such as Kyverno or the Sigstore policy-controller if you need to.
