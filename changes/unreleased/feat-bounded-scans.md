### Added
- **Workload usage rollup (E3, BUG-12):** the `workload_usage_hourly` table (migration `0052`, SQLite and PostgreSQL) keeps one row per hour, workload target, container (`""` = pod level) and node: sample, step and pod counts, CPU and memory average/p50/p90/p95/p99/max per replica, latest requests and limits, requested capacity, replica-seconds, allocated cost (with components and `cost_source`), CO2e, energy and grid intensity. The compression job re-rolls the last 24 hours every run (from raw rows, or from the hourly tables once raw rows are pruned), backfills the lookback on its first run and prunes it with `METRICS_AGGREGATED_RETENTION_DAYS`; each scan first rolls the hours collected since. Hours written behind the rollup (collection catch-up after an outage with `COLLECTION_MAX_BACKFILL` above 24 hours, `greenkube start --last`) are found through raw row-id marks (`workload_usage_rollup_marks`, migration `0053`) and re-rolled on the next run.
- **Two-way rightsizing (E9):** native CPU and memory rightsizing also proposes reliability **increases**: p99 usage above `RIGHTSIZING_INCREASE_THRESHOLD` (default `0.9`, Helm `config.recommendations.rightsizingIncreaseThreshold`) of the request, OOM kills, or a memory working set above 90% of the limit. Increases are projected by the Impact Model as negative cost deltas and kept as such; they are advisory (no GitOps action) until container resources v2.
- **Limits policy (E9):** `RECOMMENDATION_LIMITS_POLICY` (`keep` default, `remove_cpu`, `memory_equals_request`; Helm `config.recommendations.limitsPolicy`) adds limit advice to rightsizing recommendations: a CPU limit below the new request or with more than 5% throttling, a memory limit below max(request, 1.1 × max), or the policy's own change. Under `memory_equals_request`, memory decreases never go below 1.1 × the observed maximum.
- **Coverage gate for decreases (E9):** request decreases need `RECOMMENDATION_MIN_DECREASE_COVERAGE_DAYS` (default `7`, Helm `config.recommendations.minDecreaseCoverageDays`) of observed coverage, so weekly cycles are seen. Increases need none.

- **GPU power in the usage rollup (B5 with E3):** `workload_usage_hourly.gpu_watt_seconds` (migration `0060`) sums the DCGM GPU power of the pods over each hour, and the baseline rows of a bounded scan carry it as `gpu_power_watts`, so the Impact Model keeps pricing GPU energy when a GPU workload is deleted or scheduled.

### Changed
- **Memory-bounded recommendation scans (E3, BUG-12):** on SQLite and PostgreSQL, scans no longer materialize the metric rows of the lookback (up to 750,000 `CombinedMetric` objects, about 2.6 GB). The context builder reads one usage summary per target container, the hour-of-day CPU profiles and per-node usage, all computed in SQL over the rollup, plus a few baseline rows per target for the Impact Model and the evidence. Analyzers read the summaries. Namespaces that no longer exist are filtered in SQL, so their history is left out of node averages and the observed window as well. A scan of 500 pods over 14 days peaks below 200 MB RSS and runs in under 10 s on both backends. SQLite scan queries use a small page cache, no memory map and on-disk sorts. Custom repositories keep the row-loading path bounded by `RECOMMENDATION_MAX_METRIC_ROWS`.
- **Percentiles from per-step values (E9):** rightsizing, autoscaling and evidence percentiles are taken over per-step values (the per-step maximum when collected), not over averages: hourly nearest-rank percentiles, then the nearest-rank percentile of the hourly values over the lookback. A short burst now raises p95/p99 and the recommended request.
- The default lookback `RECOMMENDATION_LOOKBACK_DAYS` is now 14 days (Helm `config.recommendations.lookbackDays`), and projected savings are annualized over the span actually observed in the lookback instead of the full lookback length.
- Autoscaling, zombie, off-peak, idle-namespace and carbon-aware analysis use the pod-level aggregate of each workload (container rows no longer replace it); the Karpenter NodePool source and the node analysis read per-node average requests and usage from the usage snapshot.

### Removed
- `UNDERUTILIZED_NODE` recommendations are no longer emitted (E9): they duplicated `OVERPROVISIONED_NODE` with weaker logic. The enum value is kept for stored recommendations.
