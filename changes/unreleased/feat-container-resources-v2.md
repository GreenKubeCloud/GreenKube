### Added

- **Request increases become pull requests (H1).** A rightsizing increase (p99 close to the request, OOM kills, a working set near the memory limit) now gets a typed `container_resources` action like a decrease, with the wave-3a sizing bounds unchanged (per-replica p99 bounded by the pod, warm-up excluded, one step capped at `rightsizingMaxIncreaseFactor`). Its pull request is a reliability fix: the `reliability` label, the verb "raise resources of", a "Projected cost (reliability fix)" table with positive amounts (never a saving), a `+$X/yr` title suffix, the OOM kills, p99 and throttling it addresses, and a verification plan judged on reliability. Golden decrease PR bodies and diffs are byte-identical; new golden bodies cover an increase with a raised memory limit and a CPU increase that removes the CPU limit.
- **`automation.autoApprove.increases` (H1)**, default `false` (`AUTOMATION_AUTO_APPROVE_INCREASES`): a request increase is never auto-approved without it; the preview reports `increase_requires_approval`.
- **Limits in pull requests (H1).** Rightsizing evidence records the container's current limits and `evidence.limit_changes` (resource, `set`/`remove`, current, proposed, reason), recomputed against the final proposed request from the `RECOMMENDATION_LIMITS_POLICY` advice: an increase raises a CPU limit below the new request or throttled (or removes it under `remove_cpu`) and a memory limit below max(request, 110% of the observed maximum), and never lowers a limit; a decrease carries only the opt-in policy changes (`remove_cpu`, `memory_equals_request`), so with `keep` decreases never touch limits. A memory limit is never removed. `SetContainerResources` gains `remove_limits` (CPU only) and the action carries the limit edits.
- **Kustomize limits (H1).** The managed strategic-merge patch now writes limits, and a removed CPU limit as an explicit `cpu: null` deletion; an existing managed patch that sets limits is preserved and merged.
- **Native sidecars and init containers (H1).** Scans record where each container lives (`evidence.container_kind`: `container`, `sidecar` for an init container with `restartPolicy: Always`, `init`), actions carry `container_kind`, and raw and Kustomize planning address `initContainers`; apply detection and the pre-apply baseline read native sidecar requests, so sidecar request changes roll back automatically. Helm planners refuse sidecar edits and limit removals with an explanation.
- **Argo Rollouts (H1).** `argoproj.io/v1alpha1 Rollout` (inline `spec.template`) joins `CronJob` and `Job` as an addressable container-resources target; a Rollout with `workloadRef` fails closed.
- **OOM-rate health measurement of increases (H1).** Change measurement compares the OOM-kill rate after the rollout with the rate the recommendation observed (exact conditional binomial test, one-sided p <= 0.10): `realized` when it dropped, `not_realized` when it did not, `inconclusive` otherwise. The result is stored in `counterfactual_params.reliability` and the measurement reasons; the savings estimates keep the increase's cost as a cost.

### Changed

- **Increase health gates (H1).** For an increase made because of OOM kills, the `oom_kills` gate compares rates instead of failing on any kill, so a kill after an OOM-driven increase no longer sends it to rollback review (which would bring the kills back) unless the rate did not drop.
- **Request <= limit invariants (H1).** An increase above a known limit without a limit change gets no action; planning rejects any rendered `request > limit` (raw and Kustomize), and the Kustomize "requests only" restriction is lifted.
- A plan that edits limits no longer promises an automated rollback: its PR says to revert the pull request (the pre-apply baseline records requests only).
