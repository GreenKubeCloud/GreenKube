### Added
- **Delivery modes (F4).** `automation.delivery.mode` (`AUTOMATION_DELIVERY_MODE`): `direct` (default, GreenKube opens the PR), `patch` (an operator applies the approved plan and opens the PR) or `ci` (a CI job does, with its own token). The mode is recorded on each plan when it is approved (migration `0077`, column `automation_plans.delivery_mode`, SQLite and PostgreSQL), so a later change never re-routes an approval; `patch` and `ci` approvals queue no Git operation and need read access only. New routes: `GET /api/v1/automation/plans?status=approved&delivery=ci` (plan branch, base branch and revision, PR title and body, patch and delivery URLs), `GET /api/v1/automation/plans/{id}/patch` (the approved plan as one `git format-patch` commit with the `GreenKube-Plan` trailer; served only when the stored diff reproduces the original blobs exactly, else `409 patch_unavailable`) and `POST /api/v1/automation/plans/{id}/delivery` (`{pr_url, head_sha}`, new API-key scope `plans:deliver`, also granted to the `operator` role). A delivery report is verified through the provider before it is tracked: plan repository, base branch, deterministic plan branch (or, in `patch` mode, the `GreenKube-Plan` trailer or GreenKube footer of the PR body), open or merged, `head_sha` is the PR head, and the head holds exactly the planned file changes; the pre-apply baseline is captured then. A repeated report is idempotent (`200`, `created: false`), another PR for the same plan is `409 delivery_conflict`. The automation controller also links a PR opened from the plan branch without any report (`external_delivery` step, PR poll interval). An approved `patch`/`ci` plan waits for its PR up to 7 days after the preview TTL before it becomes `stale`. All three modes reach `pr_open` → `merged` → `synced` through the same lifecycle. Branch cleanup never deletes the branch of an externally delivered plan.
- **`greenkube plan apply-patch <id>` and `greenkube plan report-delivery <id> --pr-url …` (F4).** `apply-patch` downloads the approved patch (`GREENKUBE_API_URL`, `GREENKUBE_API_KEY` from the environment), refuses a dirty working tree or an existing branch, creates the plan branch on the plan's base revision, runs `git am --3way` and optionally pushes (`--push`); `report-delivery` is the "I opened PR <url>" link-back. Example CI workflow: `docs/examples/github-actions-greenkube-delivery.yaml`.
- **GitHub App authentication (F3).** The default Secret `greenkube-git-credentials` accepts `appId` + `privateKey` (and the optional `host`), bound to the inferred GitHub provider with the same host rules as a token and never to a non-GitHub host (`github_app_host_unsupported`, replacing `github_app_not_supported`); an explicit GitHub provider authenticates as an App when its `secretKey` is `privateKey` (the chart then also projects `appId`). For each repository GreenKube signs a 9-minute RS256 JSON Web Token, discovers the installation (`GET /repos/{owner}/{repo}/installation`), requests an installation token scoped to that single repository, caches it until five minutes before expiry, and commits as the App's bot (`<slug>[bot]`). The private key, JWT and tokens are never logged or returned. New dependency `cryptography`. App manifest with minimal permissions: `docs/examples/github-app-manifest.json`; GitLab project/group access token scopes documented in `docs/automation.md#github-app`.
- **Policy-based auto-approval (F5).** `automation.autoApprove: {enabled: false, maxRisk: low, minConfidence: 0.8, contested: false}` (`AUTOMATION_AUTO_APPROVE_*`): `POST /api/v1/automation/plans` approves a fresh preview in the same request (actor `autoapprove:<requester>`, through the normal approval checks) when the requester holds the `approve` scope, the plan is not a rollback and every recommendation is active, within `maxRisk` and `minConfidence`, not contested (a hard stop; `contested: true` is rejected by the settings and the schema), and every decrease is backed by GreenKube's own usage evidence or at least two independent consensus votes. Responses carry `auto_approved` and `auto_approve_blockers`.
- **One-click "Open PR" in the UI (F5).** Recommendation cards offer **Open PR**: the dialog previews the diff inline and one click submits the digest (**Approve and open PR**, **Approve and get the patch** or **Approve for CI delivery**); an auto-approved preview needs no click, and a preview left for the click says why. In `patch` mode the dialog links the patch and offers the "I opened PR" link-back. `GET /api/v1/automation/status` reports `delivery_mode` and `auto_approve`, the readiness `delivery` capability reports the mode and `write_credentials_required`, and eligibility's `delivery_modes` names the configured mode.
- **Warm-up ETA on the recommendation list (F7).** Cards still collecting evidence show "Collecting evidence — eligible in ~31h" from the server's `eligibility.eligible_at` (on `/api/v1` and `/api/v2` recommendations).

### Fixed
- **A pull request merged or closed while the plan operation's lease was lost is adopted (D10 remainder, BUG-52).** The reclaiming worker looked for an open PR only, so after a merge or close it re-created the deleted branch, committed again and opened a duplicate PR (or failed the reclaim). Providers now look up the newest merged or closed request of the exact branch pair (GitHub, GitLab, Gitea); the worker adopts it when its head holds exactly the planned files, and the lifecycle poller records the merge (then the sync) or the close. A terminal PR with other content fails closed (re-plan).

### Removed
- **Deprecated routes (F5, M4).** `POST /api/v1/recommendations/{id}/apply-pr`, `GET /api/v1/recommendations/{id}/apply-pr/eligibility` and `GET /api/v1/automation/operations/{operation_id}` answer `404` after their deprecation release: use `POST /api/v1/automation/plans`, `POST /api/v1/automation/plans/{id}/approve`, `GET /api/v1/automation/plans/{id}` and the recommendations' `eligibility` field.
