### Added

- **Remote Helm charts (H2):** Argo CD and Flux Helm sources whose chart lives in an HTTP Helm repository or an OCI registry can now be planned. The controller pre-fetches exactly the chart version the GitOps controller deployed (Argo CD `status.sync.revisions`, Flux `status.history[0].chartVersion`), verifies it against the digest its repository publishes (HTTP `index.yaml` digest; OCI manifest and chart-layer digests, plus the digest a Flux OCIRepository deployed), unpacks it in memory with hard limits (no links, no path escapes, packaged dependencies expanded) and stages it into the render workspace: the renderer sandbox keeps `egress: []`. Anonymous registry bearer tokens never follow a cross-host redirect; loopback, link-local and metadata addresses are always refused. Remote charts render twice and fail closed on differing output (`nondeterministic-chart-render`) instead of being rejected for merely defining `lookup`/random helpers. Plans carry the chart provenance (`remote Helm chart <reference> rendered from sha256:...`). New module `gitops/renderers/charts.py`.
- **Argo CD multi-source `$values` apps (H2):** a remote chart source plus a `ref: values` Git source plans an edit of the last values file of the values repository; discovery records the resolved chart version (`renderer_config.chart.resolved_version`).
- **Flux HelmRepository and OCIRepository charts (H2):** HelmReleases with `spec.chart.spec.sourceRef.kind: HelmRepository` (HTTP or `type: oci`) or `spec.chartRef.kind: OCIRepository` are rendered from the pre-fetched chart and edited through the managed post-renderer (discovery no longer blocks them with `remote-chart-not-in-snapshot`; Bucket sources still do). Discovery records `resolved_version` and, for an OCIRepository, the deployed `digest`.
- **Values-path mapping registry (H2):** `gitops/planning/helm_mappings.py` maps containers of well-known charts (Bitnami `resources`/`<component>.resources`/`metrics.resources`, ingress-nginx, cert-manager, podinfo, grafana, bjw-s app-template, stakater application) to their values paths; operator mappings per chart and version (`automation.helm.chartMappings`, `GITOPS_HELM_CHART_MAPPINGS`) are tried first; unknown charts fall back to a render probe of the Git values file and the chart's default values. Every candidate is render-validated; a missing or empty `resources` of a remote chart is seeded with the container's rendered resources so preset-based charts keep their limits.
- Settings `automation.helm.remoteCharts.enabled` (`GITOPS_HELM_REMOTE_CHARTS`, default `true`) and `automation.helm.remoteCharts.allowedHosts` (`GITOPS_HELM_CHART_HOSTS`), with schema validation and helm-unittest coverage.
- Fail-closed reason codes for remote charts: `chart-version-unresolved`, `chart-host-not-allowed`, `chart-registry-auth-required`, `remote-charts-disabled` (unsupported source), `chart-digest-mismatch`, `chart-digest-unavailable`, `chart-not-found`, `chart-archive-invalid`, `chart-size-limit`, `nondeterministic-chart-render` (render validation failed), `remote-chart-values-not-in-git`, `remote-chart-values-files`.
- Recorded test fixtures: a Bitnami-style chart (`tests/gitops/fixtures/charts/nginx`) served by an in-memory Docker Hub-like OCI registry and HTTP repository, and an Argo CD multi-source application (`argo-multi-source-oci.yaml`); a real-`helm` test renders the chart end to end through the planner.

### Changed

- **Several containers per Helm plan (H2):** the Argo CD values planner no longer requires exactly one container; each container gets its own (explicit, configured, built-in or probed) values path in the same values file, validated in one render. An explicit `values_mapping` for another container now reports `needs_mapping` for the remaining containers instead of `unsupported`.
- `HelmRenderer.render(remote_chart=True)` accepts remote chart dependencies only when they are vendored under `charts/`.
- `docs/automation.md`: new "Helm support" section and a corrected support table; `docs/configuration.md` documents the new settings.
