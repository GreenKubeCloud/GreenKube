### Added

- **Append-only savings ledger v2 (C6):** a new `savings_ledger_entries` table (migration `0079`, SQLite and PostgreSQL) holds every saving as a signed entry of one quantity (`cost` in the pricing currency, `co2e_g`) under one method (`projected`, `measured_allocated`, `realized_billed`, `user_declared`), with its kind (`accrual`, `reversal`, `restatement`), its book (`accrued`, `restatement`), its reason and its provenance (recommendations, change, pull request, measurement, method version). Database triggers reject `UPDATE` and `DELETE` (and `TRUNCATE` on PostgreSQL). Entries form a per-cluster hash chain: a gap-free `seq` and `hash = sha256(prev_hash || canonical JSON of the entry)`; appends are serialized per cluster and idempotent by entry key. Rollups are read-side (`savings_ledger_daily_rollup` view); nothing is compressed or deleted.
- **Dual write from the accrual path (C6):** the savings attribution job keeps writing the v1 ledger read by the legacy views, and every run is followed by a ledger v2 pass that projects the new v1 rows (an anti-join on the v1 rows that have no entry yet, from 1,000 ids below the watermark in `ledger_projection_watermarks` and from the first id in an hourly full sweep, so a v1 row committed out of id order is never lost; `greenkube_ledger_unprojected_rows{source_table}` and the `GreenKubeLedgerProjectionBacklog` alert report a backlog), reverses superseded rows (reason `supersession`) and turns drift-monitor reversals into `reversal` entries (reason `drift`, C8). A failed pass never fails the accrual and is caught up by the new `ledger-chain` loop (`greenkube_ledger_write_errors_total{reason}`).
- **Restatement of projections by measurements (C6, BUG-39):** once a recommendation is verified, each projected accrual of the measured period becomes a `reversal` plus a `restatement` entry at the measured rate, linked to the projection, the measurement and the change. Values are signed and never floored. The `accrued` book still reconciles with the v1 ledger; the `restated` total moves the measured period from `projected` to `measured_allocated`.
- **Hash-chain verification loop (C6, N7):** the leader-only `ledger-chain` controller loop (`LEDGER_CHAIN_VERIFY_INTERVAL`, Helm `config.ledger.chainVerifyInterval`, default `1h`, 1m to 24h) catches the ledger up and verifies each chain (incrementally, fully once a day and at start; a truncated tail is detected against the last verified head). Failures increment `greenkube_ledger_chain_verification_failures_total{reason}`, set `greenkube_ledger_chain_ok{cluster_uid}` to 0 (the new `GreenKubeLedgerChainVerificationFailed` PrometheusRule alert fires on it) and are stored in `ledger_chain_status`, which keeps the last head that passed so a failure stays reported until an operator resets it; `greenkube_ledger_chain_verified_entries` reports the verified size.
- **Ledger API and exports (C7):** `GET /api/v2/ledger/entries` (newest first, cursor pagination, filters `namespace`, `method`, `quantity`, `entry_kind`, `book`, `reason`, `recommendation_id`, `change_id`, `measurement_id`, `last` or both `start` and `end`), `GET /api/v2/ledger/summary` (totals per method and quantity by book, entries by kind, chain status) and `GET /api/v2/ledger/export` (`format=csv`, one row per entry with `window_share`/`window_value`; `format=focus`, FOCUS-aligned rows with `x-greenkube-*` extension columns such as `method`, `measurement-id`, `pr-url`, `co2e-g`, `saving`). The `accrued` totals and exports reconcile with `GET /api/v1/recommendations/savings`. CSV string cells are guarded against formula injection and `pr_url` is the pull request's web URL.
- **Cluster identity (N9):** the UID of the `kube-system` namespace is stored next to `CLUSTER_NAME` in `cluster_identities` the first time it is read (first resolution wins, `name:<CLUSTER_NAME>` without Kubernetes access or when the read is forbidden; a transient error, including a Kubernetes client that failed to load inside a pod, writes nothing) and keys the ledger chain. New change rows record it in `change_events.cluster_uid`. Signal ids and recommendation fingerprints are unchanged.
- **Workload deletion closes the measured accrual (C8):** the drift monitor checks that a realized change's Deployment, StatefulSet or DaemonSet still exists; HTTP 404 records `workload_absent`, and a workload still absent two hours later closes the change (`workload_deleted`), ends its recommendations' measured accrual at the first absent observation and reverses what accrued after it. A workload seen again records `workload_present`; any other answer decides nothing.
- **Pool-wide price-card control (C4):** change measurement reads the CPU and memory unit prices of every pod on the workload's node pools in both windows. A shift above 5% lowers confidence and above 20% contaminates the measurement (`pool_price_card_change`), including for changes that resized both resources, where the workload-level price check has no untouched resource. The measured workload's own pods are left out of the pool prices.
- **Accelerated change measurement for demos (`CHANGE_MEASUREMENT_ACCELERATED`, Helm `config.recommendations.changeMeasurement.accelerated`, default `false`):** lifts the 7-day minimum of the baseline window down to 1 hour, validated at startup and by the values schema; production defaults are unchanged and the controller logs a warning when it is on.

- **Quickstart change-measurement overlay (`docs/examples/quickstart/values-change-measurement.yaml`):** enables change measurement on accelerated windows (6-hour baseline, 3-minute warm-up, 72-minute post-window) on top of the quickstart values, so merged changes fill the `/changes` and `/ledger?change=…` pages and `GET /api/v2/ledger/entries?change_id=…`. A fresh cluster has no baseline for the same hours of the week: expect an `inconclusive` outcome about 80 minutes after the merge (the decision waits one hour for late samples) rather than measured savings; `make e2e` then needs `E2E_ALLOW_REGRESSION=1` and an `E2E_TIMEOUT_VERDICT` above two hours.

### Changed

- **Quickstart (`docs/examples/quickstart/values.yaml`):** the ledger loop runs every 5 minutes, so `/api/v2/ledger/*` fills and is verified during the quickstart. Merged changes are still decided by the 6-minute verifier (inside the `make e2e` verdict timeout); change measurement is the opt-in overlay above.
