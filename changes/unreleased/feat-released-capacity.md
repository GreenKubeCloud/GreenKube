### Added
- **Released capacity, projected (WP-08.1).** Every recommendation read through the API carries `released_capacity` (never persisted, derived from the stored `impact.capacity_released`): annual core-hours, GiB-hours, replica-hours and node-hours (`period: year`), the instantaneous `(current - proposed request) x replicas` in cores and GiB per replica and in total, storage GiB and LoadBalancer count for asset deletions, with units and the `projected` label. The pull-request summary has a "Released capacity (projected)" table, the recommendation list shows a "Frees ... (projected)" line and the detail page a released-capacity block. It is never converted to money and never added to cost savings; increases are negative releases ("Reserves ... more"). `impact.capacity_released` gains `storage_gib` and `load_balancers` (0 on rows stored before).
- **Released capacity, measured, and the capacity verdict (WP-08.1).** The applied detector records per-container requests and limits with each workload spec observation (migration 0140: `workload_spec_observations.container_resources`, `change_measurements.capacity`). Each decided change measurement carries `capacity`: requested cores and GiB per replica before and after (from the specs, not the metric rows), compared against the spec observed before the rollout started (or with the change's `spec_digest_before`) over the containers present on both sides (removed and added containers listed apart, classic init containers left out), the mean replicas of both windows, the request effect at the baseline replicas (`total`), core-hours and GiB-hours over the post-window, a separately reported `replica_change` that is never booked as a release (`total + replica_change = net`), and a verdict `released` / `partially_released` / `not_released` (`unknown` when the requests were not recorded) decided from the specs alone, so it exists when the cost verdict is `inconclusive` and without OpenCost or an autoscaler. Returned by `GET /api/v2/changes/{id}/measurements` and shown on the change page. Measurements decided before keep `capacity: null` and their evidence digest. Not accrued in the savings ledger yet.
- **Realization context across restarts and `IMPACT_AUTOSCALER_HINT` (IMP-12, partial).** Each resolved realization context is stored (migration 0141, table `realization_context`) and a recommendation scan in a process that has not observed the cluster yet restores it when younger than 24 hours, instead of projecting with the unobserved factor 1.0. `IMPACT_AUTOSCALER_HINT` (`none`, `cluster_autoscaler`, `karpenter`; Helm `impact.autoscalerHint`) declares the autoscaler of the nodes outside Karpenter pools when detection does not see it; `cluster_autoscaler` yields the 0.6 factor without the status ConfigMap. A projection still made with the unobserved factor reports `projected_billable_cost_annual: null` and `projection_note` "billable saving unknown: cluster not observed yet" in the API and the UI (its stored `impact` and the ranking still use 1.0). Not done: the configurable Cluster Autoscaler ConfigMap name and the autoscaler in `/api/v1/health`.
- **Recommendation export (WP-08.1).** `GET /api/v1/recommendations/export?format=csv|json` exports the active recommendations with their projected billable and allocated cost and their projected released capacity, the unit in each column name and `capacity_method: projected` (`affected_replica_hours_per_year` is the replica-hours a change applies to, not a release).

### Changed
- **Fixed-capacity clusters: lanes and ranking (IMP-03).** The lane follows the direction of the change: a request increase (or a projection with a negative allocated cost) is in the `reliability` lane, counts the incident cost it avoids and gets the `reliability_change` warning, even when the realization factor 0 makes its billable projection `-0.0`. The ranking value adds `RECOMMENDATION_CAPACITY_VALUE_WEIGHT` (default 1, Helm `config.recommendations.capacityValueWeight`) x (allocated - expected billable), reported as the `allocated_value` EV factor (money: chargeback, not billed) and in `value.components`, so request changes on fixed nodes are ranked by size instead of by risk alone. Recommendations carry `projected_allocated_cost_annual`, `projected_allocated_co2e_annual_g`, `projected_billable_cost_annual` and `projection_note` ("fixed nodes: frees capacity, bill unchanged until nodes are removed"); the recommendation list, dashboard, detail page and pull-request summary show it as "Allocated cost (chargeback, not billed)" with that note instead of hiding a 0. The Overview opportunity keeps the allocated value out of its expected value and counts those recommendations apart. Scores are recomputed at every scan and on read: no stored data to migrate, but `ranking_score` values change on every cluster (with weight 1 the value of a request change is its allocated saving).
- **Workload deletions on fixed-capacity clusters (IMP-05, Impact Model 3.0.0).** Zombie-pod and idle-namespace deletions take the pool's realization factor like a request cut, instead of 1: their reserved CPU, memory and other cost and their idle, memory and embodied CO2e are expected at the factor, while per-asset costs (storage, LoadBalancer, network) and the usage-based CO2e (dynamic CPU and GPU power) are saved whole. On fixed nodes a deletion no longer outranks every rightsizing with an overstated billable saving. `impact.co2e_expected_breakdown_annual_g` reports the expected CO2e per component and the component-matched comparison uses it. Allocation is unchanged; recommendations are re-projected at the next scan and stored projections keep the version that made them.
