### Added
- **Signal model v2 (E4).** `greenkube.signals` defines `SourceSignal`: a cluster-qualified `TargetRef` (`cluster/group.Kind/namespace/name[/container]`), a v2 `Capability` (`container_requests`, `cleanup`, `schedule`, `node_pool`...), a typed `Proposal` (`container_resources`, `replicas`, `hpa`, `schedule`, `deletion`, `node_pool`, `advisory`), the algorithm, evidence, observed window, the source's confidence and claimed savings (kept for comparison only), provenance and a raw payload trimmed to 8 KiB. `signal_id = sha256(source, target key, capability, proposal)` is stable across scans. Every v1 recommendation maps to a signal and back without loss; the v1 flat fields are computed from the target and the proposal.
- **Source SDK (E5).** A `Source` contract (metadata, `discover()`, `health()`, `collect() -> SourceBatch` with `complete` and diagnostics, a validated settings model, `SourceLimits`), a `SourceRunner` that isolates every source (probe and collection timeouts, rate limit, circuit breaker after 3 consecutive failures for 15 minutes, signal validation, API-safe error codes) and a registry with built-ins plus third-party sources loaded from the `greenkube.sources` entry points. Third-party sources contribute signals only: the runner ignores v1 recommendations from any plugin (diagnostic `recommendations_ignored`), and the registry rejects a plugin that declares a `legacy_source` or subclasses a built-in adapter, so no third-party advice reaches persistence or pull requests before consensus (E6) and risk review exist. Contract checks for any source in `greenkube.signals.testing`; developer guide in `docs/sources.md`; an installable example package in `examples/greenkube-source-example`.
- **Built-in sources on the SDK (E5).** Each native analyzer is a source (`greenkube.rightsizing_cpu`, `greenkube.orphaned_lb`...) through one analyzer adapter; `vpa` and the NodePool heuristic, renamed `greenkube.nodepool` (its v1 recommendations keep `source: karpenter`), run through the v1 connector adapter. Analyzer internals and the v1 recommendation output are unchanged.
- **Source runs and signals are persisted (E5).** Migrations `0065_source_runs` and `0066_source_signals` (SQLite and PostgreSQL): one run per source per scan (status, health, signal and recommendation counts, consecutive failures, error code, diagnostics, linked to the optimization run) and one row per distinct signal with its first and last sighting and the fingerprint of the v1 recommendation it supports. Both are pruned after 30 days. Circuit-breaker and rate-limit state survive restarts and leader changes.
- **Sources API (E5).** `GET /api/v1/sources` (metadata, enablement, status, health, last run, last success, counts, limits, and plugin or settings problems), `GET /api/v1/sources/{id}/runs` and `GET /api/v1/sources/{id}/signals`.
- **Settings:** `SOURCES_PLUGINS_ENABLED` (Helm `sources.pluginsEnabled`, default `true`) and `SOURCES_CONFIG` (Helm `sources.settings`, JSON keyed by source id; `enabled: true|false|auto` overrides `RECOMMENDATION_VPA_ENABLED`/`RECOMMENDATION_KARPENTER_ENABLED` and can turn one native analyzer off; invalid JSON is rejected at startup).

### Fixed
- **A failing native analyzer no longer makes its recommendations stale (E8).** The native source swallowed analyzer exceptions and reported a complete result, so reconciliation marked every recommendation of the failed analyzer stale. The native result is now incomplete when an analyzer fails (and, with one source per analyzer, the v1 source `greenkube` is incomplete for that run).
- **Helm: `config.recommendations.vpaEnabled: false` and `karpenterEnabled: false` were ignored.** The ConfigMap used `default true`, which turns `false` into `true`; both connectors could not be disabled from Helm.
