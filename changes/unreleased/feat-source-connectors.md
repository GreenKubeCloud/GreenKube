### Added
- **Goldilocks provenance in the VPA connector (G1).** VPAs labelled `creator=Fairwinds` and `source=goldilocks` produce signals with `source_id: goldilocks` (`algorithm.name: vpa-recommender`, `source_ref: <ns>/<vpa>`), every other VPA with `source_id: vpa`; both carry the new signal field `engine_family: vpa`, so consensus counts a Goldilocks VPA and a user VPA on the same container as one vote (`SourceSignal.engine`). Signals are emitted per VPA object and include increases; v1 recommendations are unchanged. `lowerBound`, `upperBound` and `uncappedTarget` travel in `raw`, a target at 90% or more of its `upperBound` is flagged in `evidence.data.risk_hints.volatility`, and the run reports skipped VPAs by update mode, Goldilocks VPAs and the namespaces opted in with `goldilocks.fairwinds.com/enabled` (warning for opted-in namespaces without Goldilocks VPAs). Built-in sources may declare other source ids they emit (`also_emits`); plugins may not. See `docs/sources/goldilocks.md`.
- **Push API and public signal schema (G6).** `POST /api/v1/signals` (scope `signals:write`) accepts a batch `{source_id: "push:<client>", complete, signals}` of up to 5,000 signals, idempotent on `signal_id`; `complete: true` withdraws the client's earlier signals. Schema errors answer `422` with RFC 6901 JSON pointers. The schemas `schemas/signal.v1alpha1.json` (SourceSignal minus `schema_version`, `signal_id`, `source_id`, `provenance`, `fetched_at`) and `schemas/signal-batch.v1alpha1.json` are generated from the server models (`python -m greenkube.signals.connectors.push schemas`) and checked by a test. A built-in `push` source replays pushed signals received within `max_age_hours` (default 168) into each scan, so they are validated, recorded in `source_runs`/`source_signals` and reach recommendations only through consensus. Curl example in `docs/sources/push.md`.
- **Signal inbox (migration `0070`, SQLite and PostgreSQL).** `source_inbox_batches` (one row per accepted push: source, time, completeness, counts, pushing principal, diagnostics) and `source_inbox_signals` (current pushed signals per source and `signal_id`); rows not pushed again for 30 days are pruned on the next push.
- **Robusta KRR connector (G2).** `POST /api/v1/sources/krr/reports` (scope `signals:write`, `?complete=false` for partial reports) parses `krr <strategy> -f json` output pinned against a KRR 1.x report fixture (shaped after KRR's `Result` model): one `ContainerResourcesProposal` per container and resource, increases included, strategy settings in `algorithm.params` and the history window, severity as a confidence hint, `"?"` and unchanged values skipped with diagnostics, unknown fields ignored. A report covering several clusters (`--all-clusters`) is refused with `422` (`multiple_clusters`) unless `?cluster=<kubeconfig context>` selects this GreenKube's cluster, so another cluster's advice never lands on same-named workloads here. The `krr` source replays the stored report into scans. Optional job mode: `sources.krr.job.*` renders a CronJob (disabled by default) running `robustadev/krr` pinned by digest with its own read-only ClusterRole, and uploading the report with a `signals:write` key from a Secret. See `docs/sources/krr.md`.
- **Kubecost connector (G3).** The `kubecost` source probes the Kubecost version and uses a versioned path map (2.x and 3.x, overridable per path with `SOURCES_CONFIG.kubecost.paths`): request sizing v2 → `ContainerResourcesProposal` (Kubecost's monthly savings in `source_estimate`), abandoned workloads → review-only `DeletionProposal` with `capability=cleanup` (evidence basis `network_traffic`, `deletion_requires_review`), cluster or node-group sizing → high-risk `AdvisoryProposal` (only with a positive saving). Abandoned workloads' generated owners (ReplicaSet, Job) are resolved to their Deployment or CronJob through the workload inventory. Several clusters without `cluster_id` are reported, not guessed, node-group sizing included; a `404` endpoint is a diagnostic. Settings: `url`, `version`, `window`, `algorithm_cpu`/`algorithm_ram`, `q_cpu`/`q_ram`, `target_cpu_utilization`/`target_ram_utilization`, `filter`, `cluster_id`, `abandoned_workloads`, `node_group_sizing`, `paths`, `timeout_seconds`. Free-tier licensing note in `docs/sources/kubecost.md`.
- **NodePool policy advice (G5).** `greenkube.nodepool` also emits high-risk advisory signals (no v1 recommendation, no pull request until H7) with the suggested NodePool patch: `consolidationPolicy: WhenEmpty`, `consolidateAfter` above 1 hour or `Never`, on-demand-only capacity on pools whose observed workloads are all stateless (allow spot), and amd64-only pools (allow arm64 where images are multi-arch). See `docs/sources/nodepool.md`.
- **Karpenter events in the RealizationContext (G5, B6).** NodeClaims (claim → pool) and Karpenter `DisruptionBlocked` events now block their pool (factor × 0.5, with the event in the reasons); `Unconsolidatable` events are listed in the reasons. Unreadable events are reported, never read as "no blocker". The chart's ClusterRole gains `list` on core `events`.
- Connector pages `docs/sources/goldilocks.md`, `krr.md`, `kubecost.md`, `push.md` and `nodepool.md`.

### Fixed
- **Karpenter NodePool requirements were never read.** The collector read `spec.requirements`, but NodePools declare them under `spec.template.spec.requirements` (v1 and v1beta1), so every pool looked unconstrained. It now reads the template (and still accepts the old location), and records `consolidateAfter`.
