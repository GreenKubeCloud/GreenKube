### Added

- **Fairwinds Polaris connector (G4).** `POST /api/v1/sources/polaris/reports` (scope `signals:write`, `?complete=false` for a partial audit) parses `polaris audit --format=json` (Polaris 9.x/10.x `AuditData`): every failed `warning`/`danger` check on a controller, pod spec or container becomes a `capability=hygiene` advisory signal (kind `CPU_REQUESTS_MISSING`, `RUN_AS_ROOT_ALLOWED`...), never a pull request; passing and `ignore` checks are counted in diagnostics. The `polaris` source replays the audits from the inbox and adds a **native follow-up** for `cpuRequestsMissing`/`memoryRequestsMissing`: when GreenKube observed the container (at least `RECOMMENDATION_MIN_SAMPLES` samples) and still sees no request, it proposes p95 × `RIGHTSIZING_HEADROOM` as a `container_requests` signal (`greenkube.requests_from_usage`, engine family `greenkube.hygiene`), which becomes a recommendation through consensus; its current request is zero, so it is an increase delivered by review, never directly. Optional CronJob `sources.polaris.job` (disabled by default; `quay.io/fairwinds/polaris` 10.1.8 pinned by digest, read-only ClusterRole without Secrets or ConfigMaps, upload with a `signals:write` key, NetworkPolicy rule to the API). See `docs/sources/polaris.md`. Popeye is not ingested yet.
- **GKE recommender insights connector (G7).** The `gke` source reads Google Recommender insights of subtypes `WORKLOAD_OVERPROVISIONED`/`WORKLOAD_UNDERPROVISIONED` through the GKE metadata server (Workload Identity, no key file, read only). The insight type is discovered at runtime (`v1beta1/insightTypes`, every `google.container.*` type) unless `insight_types` pins it; insights are read in the cluster's zone and region. Container recommended requests in the insight content become `ContainerResourcesProposal`s (increases included); insights without readable values stay advisory signals; an insight is attributed to this cluster only when its target names this project (id or number), this cluster's exact location and its name, so a same-named regional cluster's insights are skipped (`other_cluster`). Every batch reports GKE's coverage gaps (VPA-managed requests, HPA target metrics, workloads younger than three days) as the `gke_coverage` diagnostic. See `docs/sources/gke.md` (Workload Identity setup).
- **Azure Advisor connector for AKS (G9).** The `azure_advisor` source reads Advisor recommendations of the subscription (`api-version=2023-01-01`) through Azure Workload Identity and keeps those about this AKS cluster (`impactedValue`, optional resource group) as high-risk `AdvisoryProposal`s on the `Cluster` target (`node_pool` for autoscaler and node-pool advice, `hygiene` otherwise), with Advisor's savings in `source_estimate`. Paging never follows a `nextLink` to another host than Resource Manager (the ARM token stays there; diagnostic `foreign_next_link`). Unavailable until `subscription_id`, `cluster_name` and the Workload Identity variables are present. See `docs/sources/azure-advisor.md`.
- **Karpenter metrics in the RealizationContext (G5, B6).** When Karpenter runs and `PROMETHEUS_URL` is set, the controller reads `karpenter_voluntary_disruption_decisions_total` (7-day increase by reason), `karpenter_voluntary_disruption_eligible_nodes` and `karpenter_nodepools_cost_total` (7-day increase per NodePool). Consolidation decisions are listed in the reasons of consolidating pools; no consolidation decision over 7 days while nodes are eligible is a blocker (factor × 0.5); the pool cost increase is recorded as the pool's `observed_cost`. Metrics that are not exported change nothing (never read as zero); an unreachable Prometheus is noted as "Karpenter metrics could not be read".
- Consensus across three independent engine families (VPA/Goldilocks, KRR, GKE recommender) on the demo container is covered by an integration test (E6, G7).

### Changed

- **A push client is bound to its API key (G6).** A scoped API key may only push `POST /api/v1/signals` batches as `push:<key name>` (the key name lowercased, other characters than `[a-z0-9_.-]` replaced by `-`); any other `source_id` answers `403 push_client_mismatch`, whatever the key's scopes. Signed-in administrators and the deprecated bootstrap key are not bound. Existing keys named after another client must be recreated under the client's name.
- **Kubecost 3.x path map checked against the documented API (G3).** The IBM Kubecost self-hosted 3.x API directory still documents the Cluster Right-Sizing Recommendation API and no node-group sizing API, so the 3.x map now reads node-group sizing from `/model/savings/clusterSizingETL` (earlier builds guessed `/model/savings/nodeGroupSizing`). The documented answer, keyed by cluster id with `recommendations.single`/`multi`, is read for this cluster only (the best strategy's monthly saving, every strategy in `evidence.data.monthly_savings_by_strategy`); the flat shape is still accepted. The Kubecost fixtures are labelled synthetic in a `_provenance` field, as are the new Polaris, GKE and Azure Advisor fixtures.

### Fixed

- **`GET /api/v1/recommendations/active?source=` ignored the consensus provenance (E6/G1):** a recommendation chosen from VPA but supported by Goldilocks or KRR was not listed for `?source=goldilocks` or `?source=krr`. The v1 filter now also matches `consensus.source_ids` and `sources`, like `GET /api/v2/recommendations`.
- **Kubecost 3.x node-group sizing never produced advice (G3):** the 3.x path map pointed at an undocumented endpoint, and the parser only read a flat `totalMonthlySavings`, so the documented per-cluster answer was reported as "no positive saving".
