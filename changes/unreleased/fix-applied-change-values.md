### Added
- **`no_effective_change` (fail closed):** a pull request that would change nothing is never opened. The eligibility check blocks a proposal equal to the current request after unit normalization (`1Gi` = `1024Mi`, `0.5` = `500m`); plan creation answers `409 no_effective_change` when the Git source already declares the proposal (raw, Kustomize, Helm values and Flux HelmRelease planners); the plan worker fails the plan with reason `no_effective_change` before any branch, commit or PR when the live workload already runs every proposed request.
- **Git provider verification state:** `GET /api/v1/automation/status` reports `status: verified` with `last_checked_at` once the worker opened or adopted a pull request, and `status: error` with `last_error_code` `auth_failed` (401) or `permission_denied` (403) when the provider refuses the token. Configuration changes that keep the endpoint and credential reference keep the verification.
- Recommendation event types `pr_opened`, `pr_closed` and `stale` (reason `no_effective_change`).

### Changed
- **`pr_open` recommendation status:** a recommendation whose pull request is open, merged or syncing is `pr_open` (it stayed `active`), set in the same transaction as the GitOps action status; a PR closed unmerged or a failed action returns it to `active`. Scans no longer rewrite its baseline and proposal or insert a duplicate, and it no longer goes stale or expires while the PR is in flight. `GET /recommendations` and `/recommendations/active` still list it with the `pull_request_open` blocker. Migration `0061` aligns the rows of PRs open at upgrade time.
- A recommendation with a typed action but no plan in flight (action status `none`, `failed` or `closed`) whose proposal is already live is recorded as applied (`detected`) instead of being offered again.
- The Realized Savings cards show each request change as baseline → live value after the change (with the proposal when it differs) and flag a recorded change whose live request still equals the baseline as **live request unchanged**.

### Fixed
- **Merged PRs showed identical before and after requests (user report):** a scan regenerating an applied rightsizing copied its `current_*` request, read from the hourly usage rollup whose latest bucket still holds the replaced request for up to an hour after the rollout, into `actual_*`, so a merged 400m → 10m change was stored as 400m → 400m and its realized savings dropped to zero (e2e defect "actual reverts to the pre-change value"). Scans now never rewrite `actual_*`, the baseline or the savings of an applied rightsizing.
- **Phantom applied changes:** apply detection recorded a recommendation as applied when the untouched live request lay within the apply tolerance of the proposal (a 20Mi → 23Mi increase on a 20Mi request), and when the matching rollout completed months before the recommendation existed; such cards showed identical before and after values. The live request must now have moved from the baseline toward the proposal, after the recommendation was created.
- The recommendation status stayed `active` while its pull request was open, so scans could rewrite the baseline and proposal of a change under review (e2e defect).
- **Regenerated recommendations re-offered or recorded twice after a change:** a scan within the hourly rollup lag after a merged change regenerated the pre-change advice (400m → 10m while 10m was live) as a new active recommendation, and apply detection could record it as a second applied change with its own measurement and double-counted savings (StatefulSets, DaemonSets and Deployments without a `Progressing` time). The upsert now drops a rightsizing that restates a change `verifying`, `verified` or in `rollback_review` within six hours, and apply detection retires a recommendation whose live request is a change already recorded (or that landed before it was created) as `stale` with reason `no_effective_change` instead of recording or offering it again.
- **Data repair (migration `0061`):** merged rightsizing changes (`application_method = pr_merge`, applied or measured) whose `actual_*` request an old rescan had reverted to the baseline get that value cleared (unknown), together with the realized savings zeroed from it, so they no longer show a false "live request unchanged". Changes detected outside a pull request are left as recorded.
- The Git provider status stayed `unverified` after successful pull requests (e2e defect).
- Regression test: pull-request titles, bodies, labels and commit messages render enum fields as values (`low`), never as `RiskLevel.LOW` (e2e defect, fixed by PR template v2).
