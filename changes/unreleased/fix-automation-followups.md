### Added
- **GitHub App installation selection as the allowlist (F3, F12).** With GitHub App credentials, the readiness reconciler lists the repositories the App is installed on (`GET /app/installations`, `GET /installation/repositories`, every 5 minutes) and makes them the allowlist of the inferred GitHub provider; `@discovered` keeps the whole selection, explicit `automation.repositoryAllowlist` patterns narrow it (repositories an administrator allowed from the UI stay allowed when the App is installed on them), and a discovered repository outside the selection is dormant with `github_app_not_installed`. A failed read keeps the last known selection.
- **Default credentials Secret read through the Kubernetes API (F12).** `greenkube-git-credentials` is read by name (`get`, and a `watch` selected by `metadata.name` in the controller) through a new Role limited to its `resourceName` (`<release>-git-credentials`, bound to the api, controller and worker service accounts; Secrets are never listed). Creating or deleting the Secret takes effect on the next readiness tick (within 60 s) instead of after the kubelet refresh of the projected volume, which stays the fallback when the API cannot be read. Values are kept in memory only and never logged.
- **Signed commits through the GitHub App (J8).** Commits GreenKube creates as a GitHub App omit author and committer, so GitHub signs them and shows them as Verified; the commit result records GitHub's `verification.verified` and `reason`. GitLab and Gitea create API commits server-side and accept no client signature, so instead of a signing-key Secret the docs describe the platforms' own signing (GitLab web commit signing, Gitea `[repository.signing] CRUD_ACTIONS`).
- **Patch-mode linkage by the `GreenKube-Plan` trailer (F4).** At the PR poll interval the controller lists the open pull requests targeting the base branch of approved `patch` plans and links one opened from any branch whose description or commit messages carry the plan's trailer (or whose description carries the GreenKube footer), through the same verification as a delivery report. New provider reads `list_open_pull_requests` and `list_pull_request_commit_messages` (GitHub, GitLab, Gitea).
- **Degraded provider features.** Migration `0099` adds `gitops_provider_feature_notes`; `GET /api/v1/automation/status` lists `degraded_features` per provider.

### Changed
- **Evidence warm-up is relative to the history since install (F7).** `minCoverage` is evaluated against the data available since the first collected sample, capped at the lookback, both in the recommendation `eligibility` (`warm_up()`) and in the policy evaluator's `sample_count_coverage` gate (observed `coverage_since_install`); `eligible_at = first sample + minSamples query steps`.
- **Setup checklist names GitOps controller families.** The `gitops_controllers` check lists `argocd` and `flux` instead of the CRD kinds (`flux_kustomization`, `flux_helm_release`); the readiness `discovery` details keep the kinds in `source_kinds`.

### Fixed
- **Best-effort permission refusals no longer mark the provider in error.** A `403` on labels, reviewers, the validation status, the status comment or CODEOWNERS reads (for example a token without the Issues permission) keeps the provider `verified` and records a degraded feature note, cleared after the next successful call of that feature.
- **PR feedback with read-only credentials.** The lifecycle comment is never written while the `patch` or `ci` delivery mode is configured, nor on a plan approved for `patch` or `ci` delivery (F4, J5).
- **Planning a non-active recommendation** (`POST /api/v1/automation/plans`) answers `409 not_active` instead of `422 requires_container_target`, also when a recommendation grouped with it is no longer active.
