### Added
- **Persisted controller loop heartbeats (M8, F8).** Every controller replica runs a `controller-heartbeat` loop (every 30 s, leader or standby) that writes its loop registry snapshot to the new `controller_heartbeats` table (migration `0076`). `GET /api/v1/automation/status` returns `controller`: `healthy` (a fresh leader whose loops are all ready), `leader`, `available`, `stale_after_seconds` and, per replica, `leader`, `ready`, `stale`, heartbeat age and the per-loop snapshot (state, last success, consecutive failures, last error code). The API runs no loop, so this is the only place it can report controller loop state.
- **Controller loop alerts.** The chart's PrometheusRule (`monitoring.prometheusRule.enabled`) gains the group `greenkube.controller` with `GreenKubeControllerLoopFailing` (a loop failed 3 ticks in a row for 10 minutes), `GreenKubeAutomationLoopStale` (the `automation-controller` loop has not succeeded for 10 minutes) and `GreenKubeNoActiveController` (no controller holds the Lease, or none is scraped, for 5 minutes). `monitoring.prometheusRule.controllerAlerts: false` leaves them out.
- **Evidence reliability signals.** `RecommendationEvidence.oom_events` (it was always `null`) and the new `cpu_throttling_ratio` carry the OOM kills and CPU throttling of the scan's usage summary over the lookback; `null` when no source reported them.
- **`E2E_RESUME_MAX_AGE`** (default 6 hours): with `E2E_FRESH=0`, the age beyond which `hack/e2e/loop.sh` does not resume from a merged pull request.

### Changed
- **Deletions are never low risk.** Zombie pods and orphaned load balancers are `medium`, idle namespaces and orphaned volumes `high`, and every deletion carries the risk factor `irreversible_deletion` (a revert cannot bring back a deleted pod, namespace, volume or external address).
- **JVM confidence in the risk model.** The halved confidence of a memory decrease on a suspected JVM (`confidence_factors.jvm_suspected`) is applied by `risks.assess`, with the JVM risk factors, instead of by the enrichment step, so every caller of the risk model gets it.
- **HPA gate truthfulness (D13).** The HPA gate blocks a change only when an HPA scales on a `Utilization` target of the changed resource (a share of the request). `AverageValue` and `Value` targets compare raw usage, which a request change does not move: they pass with a warning. An unknown target type still blocks.
- **Git provider verification.** Any successful authenticated call through the provider registry marks the provider `verified` (with `last_checked_at`): a repository archive fetch for a plan preview, pull-request polling, branch cleanup, not only a pull request opened by the plan executor. A 401 or 403 sets `error` (`auth_failed`, `permission_denied`); transient errors leave the state as it is. An unchanged state is rewritten at most every 5 minutes per provider.
- **`greenkube.core.scheduler`** keeps only `parse_interval_seconds` and `seconds_until_boundary`.

### Fixed
- **Phantom "detected" changes (wave 3a follow-up).** Applied rows written by the old apply detector while the live request never moved from the baseline (`actual_*` equal to `current_*`, method `detected`), or matched to a rollout that predates the recommendation, stayed in the applied family with their savings and change measurement. An idempotent repair, run on every `recommendation-lifecycle` tick, moves them to `stale` with a `retired` event (code `phantom_apply_detection`), clears their realized savings, supersedes their savings-ledger rows and closes their change measurement (`retired`) when every member of the change is a phantom. It acts only on evidence: the frozen baseline's rollout time, or the newest rolled-up request, observed after `applied_at`, still equal to the baseline. A detected change whose live request reached the proposal (its `actual_*` reverted by an old rescan) is left alone.
- **The latest request lagged a rollout to another node.** A usage summary took the hour's maximum request over its node rows, so after a rollout that moved a pod to another node the replaced request stayed visible until the next hour. The rollup now records each row's newest-sample offset (`workload_usage_hourly.latest_sample_offset_seconds`, migration `0076`) and the SQL and in-memory summaries take the requests and limits of the newest sample.
- **Warm-up exclusion for hours re-rolled from compressed tables (E9).** Hours rolled from the compressed hourly tables (raw rows pruned) kept every point, so a startup spike sized requests again once raw rows were gone. A pod whose restart count rose since the previous compressed hour, or that is new in the hour, now leaves the percentiles (or counts with its hourly average when it is the only point); the maximum keeps its peak.
- **Bare-metal load balancers carried a cloud bill.** An orphaned `LoadBalancer` Service whose address comes from MetalLB, Cilium LB-IPAM or kube-vip was projected at `LOAD_BALANCER_COST_PER_MONTH`. Without an OpenCost cost it now projects no cost saving (`cost_source` `none`, detail `bare_metal_load_balancer:<allocator>`) and the description says why.
- **A second HPA on a workload was ignored (D13).** Discovery kept one HPA per target workload, so a CPU-utilization HPA listed before a memory HPA was dropped and a CPU change passed the HPA gate. Every HPA of the workload is now kept and checked.
- **The e2e resume picked up old merged pull requests.** With `E2E_FRESH=0`, `hack/e2e/loop.sh` resumed from any merged GreenKube pull request of the last 7 days, including the one of a completed earlier loop, and waited on its old change. It now resumes from an open pull request, or from a merged one only while its plan is `merged` or `synced` and it was merged at most `E2E_RESUME_MAX_AGE` ago (`hack/e2e/resumable-pr.jq`).

### Removed
- **`greenkube.core.scheduler.Scheduler`**, unused since every controller job runs in the loop registry (M8).
