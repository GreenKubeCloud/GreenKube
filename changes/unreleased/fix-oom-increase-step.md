### Fixed

- **An OOM-driven memory increase now takes one decisive step instead of creeping by 10% (live e2e).** An OOM-killed container was sized from its limit × 1.1 or its observed maximum × 1.1; with request = limit and short spikes, a workload that needed far more than its limit climbed 32Mi → 36Mi → 40Mi …, one pull request, merge and measurement window per step. When the working set reached 90% of the limit (killed at the limit, true need unknown) the step is now `RIGHTSIZING_MAX_INCREASE_FACTOR` (default 2) × the limit; after a short spike the samples missed (observed maximum below 90% of the limit) it is max(observed maximum × 1.1, limit × 1.5), never above the configured factor. The step stays bounded by `RIGHTSIZING_MAX_INCREASE_FACTOR` × the current request, and the memory limit is still raised above the new request with headroom (32Mi request = limit → 64Mi request, 71Mi limit).
