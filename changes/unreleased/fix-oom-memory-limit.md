### Fixed
- **An OOM-driven memory increase did not raise the memory limit with headroom (live e2e).** A container with request = limit = 24Mi was OOM-killed; GreenKube's bounded increase raised the request to 48Mi and set the limit to 48Mi too, with no headroom above the request. The kernel kills at the limit, so the kills went on and the change went to `rollback_review`. An OOM-driven memory increase, or one whose new request reaches or exceeds the memory limit, now raises the limit to `max(limit × the request's factor, 110% of the observed maximum)`, bounded by `RIGHTSIZING_MAX_INCREASE_FACTOR` × the old limit and always at least 10% above the new request (24Mi/24Mi becomes 48Mi/53Mi), rendered by the raw, Kustomize, Helm values and Flux post-renderer planners. A limit is never lowered and a memory limit is never removed; a non-OOM increase that stays below the limit leaves it alone.

### Changed
- **An OOM-driven memory increase that cannot raise the limit stays advisory.** Under `RECOMMENDATION_LIMITS_POLICY=memory_equals_request` the limit must equal the request, so such an increase now explains why and names the limit to set by hand (`oom_headroom_forbidden`) instead of opening a pull request that could not stop the kills. The action builder also refuses any OOM-driven increase whose limit changes do not lift the limit above the new request.
- **Reliability measurement:** a memory increase that kept or lowered a known memory limit keeps the strict "any OOM kill fails" gate instead of the OOM-rate comparison, since it cannot cure kills that happen at the limit.
