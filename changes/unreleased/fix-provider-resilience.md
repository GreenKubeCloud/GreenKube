### Added
- **Abandon a stuck plan (D10).** `POST /api/v1/automation/plans/{plan_id}/abandon` (`approve` scope: operator or admin) fails a plan stuck in `applying`: it cancels the plan's operation unless a worker holds a live lease, closes its pending pull-request records and releases its recommendations, audited with the caller and an optional reason (`abandoned_by_operator`). Refused when a pull request was already recorded for the plan, or when the deterministic plan branch holds an open pull request that was never recorded.
- **Git provider rate-limit metric and alert (D5).** `greenkube_git_provider_rate_limited_total{provider}` counts rate-limited provider responses; the PrometheusRule adds `GreenKubeGitProviderRateLimited` (group `greenkube.loop`, warning after 30 minutes).

### Changed
- **The controller health gate understands a self-caused degraded Argo CD app (D13).** An increase-only reliability plan (every recommendation raises a CPU or memory request; limits are only raised, or a CPU limit removed) is no longer blocked by `controller_unhealthy` when the Application's live status shows that the only unhealthy resource is the plan's target workload (`Degraded` or `Progressing`), with no `*Error` condition and no failed sync operation. The check's message explains the decision; suspended controllers, Flux controllers, sync errors, other unhealthy resources or an unreadable Application still block.

### Fixed
- **Plans stuck in `applying` forever (D10).** An operation that exhausted its retries after the worker wrote its `pending` pull-request record (a crash after opening the PR, then an expired last lease) left the plan `applying`, ignored by PR polling and blocking every new plan of the workload. The operation reconciler now looks up the deterministic plan branch: a pull request holding exactly the planned files is adopted (`pr_open`, audit reason `pull_request_adopted`), otherwise the records move to `error` and the plan to `failed` so the recommendations can be planned again.
- **Git provider rate limits failed plans and marked providers `permission_denied` (D5).** GitHub `403` responses with `x-ratelimit-remaining: 0` or a secondary rate-limit message, and `429` responses from any provider, are transient: the reset time comes from `Retry-After`, `X-RateLimit-Reset` or `RateLimit-Reset` (60 seconds when absent, at most an hour), a plan operation is rescheduled at that time without consuming an attempt, and the provider state is never set to `permission_denied` (the preflight reports `provider-rate-limited`). Inline retries no longer sleep a fixed 50–100 ms through a rate limit, repository archive downloads are classified the same way, and a header-less GitHub secondary limit is rescheduled instead of retried immediately.
- **Plan branches were created from the moving base branch (D7).** The deterministic plan branch is now created at the exact commit the plan was validated on (its base revision or the verified moved head), so a commit landing between validation and branch creation can no longer leak into the pull request or fail the plan. Gitea creates it with `old_ref_name` and fails closed (removing the branch) on releases that ignore it.
- **Two plans for one workload (D6, D12).** The workload busy check was check-then-act and not repeated at approval. Plan creation and the approval transition now re-check it in the same transaction under a per-workload lock (PostgreSQL advisory lock; SQLite transactions are serialized): concurrent previews for one workload yield one plan, and approving while another plan of the workload is approved or delivering returns `409 workload_plan_already_exists`. Rollback plan creation runs the same atomic check (tolerating the original plan).
