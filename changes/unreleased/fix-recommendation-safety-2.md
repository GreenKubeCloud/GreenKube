### Added
- Advice inserted for a container after its rightsizing change was recorded names that change: `previous_recommendation_id` and `previous_change_id` on the recommendation (migration 0131, SQLite and PostgreSQL), so the UI and the ledger can relate an OOM-driven increase to the decrease it follows (REC-01).
- Ignored recommendations show `changed_since_ignored` ("Advice changed since you ignored it" on the Ignored tab) when a later scan produced materially different advice, recorded once as a `changed_while_ignored` event (REC-06).

### Fixed
- The run diff no longer reports as `new` a record the repository did not write: `upsert_recommendations` reports one outcome per record (`inserted`, `revised`, `refreshed`, `queued`, `kept`, or not written: `absorbed`, `pr_open`, `applied`, `ignored`) and returns only the number of records that have an active row; the scan's persisted recommendations, `recommendation_count` and `new_count` count only those (REC-01).
- Ignoring a recommendation now survives the next scan (REC-06): the same advice is no longer inserted again as a new active row beside the ignored one, and restoring it gives exactly one active row. Migration 0132 (SQLite and PostgreSQL) merges existing duplicates (an active twin of an ignored or `pr_open` row, an ignored twin of a `pr_open` row and older duplicate ignored or `pr_open` rows become `stale` with the reason `superseded_by_ignored`) and adds a unique index on the fingerprint of `active`, `ignored` and `pr_open` rows. Ignoring a stale or expired row whose advice is active again retires that active twin; ignoring it while the same advice is in an open pull request returns `409`.
- A rightsizing decrease no longer flaps (REC-03): its target is raised to the decrease floor max(⌊p99 / `RIGHTSIZING_INCREASE_THRESHOLD`⌋ + 1, ⌈p99 × `RIGHTSIZING_HEADROOM`⌉), so applying it and scanning again with unchanged usage proposes nothing (before, any workload with an occasional peak got a decrease, then an increase, then the same decrease, forever). A memory decrease never goes below the observed maximum × 1.1 under every limits policy (before, only under `memory_equals_request`), and under `memory_equals_request` never below max / 0.9 so the peak stays under the limit pressure line. Under `memory_equals_request`, a memory increase now covers max(max × 1.1, max / 0.9) since the limit becomes the new request. Active decreases are recomputed by the next scan; no stored data changes.
- Proposals that alternate between two nearby values no longer create a new revision at every scan (IMP-13): a lower request is held within max(5%, `RECOMMENDATION_MIN_CPU_MILLICORES` for CPU, 16 MiB for memory) and, beyond it, becomes a new revision only after 3 consecutive scans proposed it (`pending_revision` records the candidate, migration 0133, SQLite and PostgreSQL); a higher request is still taken at once beyond 5%.
