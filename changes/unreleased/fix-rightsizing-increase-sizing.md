### Added

- **Increase step cap (E9, USER BUG 2):** `RIGHTSIZING_MAX_INCREASE_FACTOR` (default `2.0`, Helm `config.recommendations.rightsizingMaxIncreaseFactor`) caps one request increase at that multiple of the current request unless OOM kills back it. The reason states the cap and the uncapped target; the next scan re-evaluates once the step is applied.
- **Warm-up exclusion (E9, USER BUG 2):** `RIGHTSIZING_WARMUP_MINUTES` (default `10`, Helm `config.recommendations.rightsizingWarmupMinutes`, `0` disables) leaves the points after a container restart or a new replica out of the usage percentiles of the `workload_usage_hourly` rollup and of row-built summaries, so startup spikes (WAL replay, JIT, cache fill) do not size requests. The maximum keeps every point; a restart in the last minutes of an hour still excludes the next hour's first points.
- **Reliability signals filled by scans (E9 remainder):** each scan fills the usage summaries with `oom_kill_count` (kube-state-metrics `OOMKilled` restarts over the lookback, or cAdvisor `container_oom_events_total`), `throttling_ratio` (cAdvisor CFS periods) and a `jvm_hint` read from the pod specs (`JAVA_TOOL_OPTIONS` and similar variables, `-Xmx`/`-Xms`, a `java` command, JVM image names). Unreadable signals stay unknown. The risk profile now reads them: OOM and throttling history, and a JVM hint marks memory decreases `jvm_heap_not_observable`, halves their confidence and explains it in the reason.
- Limit advice of native rightsizing is kept as structured `LimitAdvice` (resource, action, reason, current and minimum limit) on the proposal; the description text is unchanged.
- Pod-level memory fallback: when the kubelet exports no container series (e.g. Minikube with the Docker driver), the pod cgroup working set is collected as pod-level usage, like the CPU fallback.

### Changed

- **How increases are sized (USER BUG 2):** the target is the per-replica p99 (warm-up excluded) × `RIGHTSIZING_HEADROOM`; the observed maximum × 1.1 raises a memory target only with OOM kills or a working set above 90% of the limit. The reason says which rule sized the increase. See "How GreenKube sizes increases" in `docs/recommendation.md`.
- Usage known only for the whole pod (no container series) never yields a request increase: the analyzers skip it with the reason `pod_level_usage_only`. Pod-level decreases stay advisory and say "Pod-level usage only" in their reason.
- Pod rows written by the range collection carry their workload owner, and the usage rollup resolves a pod's owner from any of its rows, so the replicas of a StatefulSet share one usage target instead of one `Pod` target each.

### Fixed

- **USER BUG 2 — absurd request increases (a Prometheus container from 400Mi to 1287Mi / 1214Mi on Minikube):** on clusters where cAdvisor only exports pod cgroups, a container's usage came from the Kubernetes Metrics API, whose container working set (cri-dockerd) counts page cache that the pod cgroup's working set excludes: ~756Mi for a container in a ~566Mi pod, growing with Prometheus's memory-mapped TSDB. The increase was then sized from max(p99 × 1.2, max × 1.1) of those samples. Metrics API container samples that add up to more than their pod cgroup (working set or CPU, +5% tolerance) are now scaled to the pod value and flagged `container_usage_exceeds_pod`, and the analyzers bound a container's increase statistics by its pod-level summary, which also covers rows collected before the fix. A pod cgroup working set below one memory page (cAdvisor reported 0 or 8 bytes for hours) is a gap, not a measurement. Replaying the recorded data now gives one StatefulSet recommendation, 400Mi → 747Mi, without the step cap. Regression fixture: real Prometheus and kubelet responses recorded on Minikube (`tests/core/fixtures/prometheus_k8s_metrics_api_minikube.json`).
- Duplicate cAdvisor series of one container (kubelet `/metrics/resource` scraped next to `/metrics/cadvisor`, two scrape jobs, two cgroup paths of one container) were summed per container, doubling usage the same way. CPU and memory usage queries now use `max` per container and the range collection merges duplicate series with `max`.
- The kube-state-metrics OOM-kill count only counts restarts whose termination reason at that restart is `OOMKilled`; a liveness-probe restart after an older OOM kill in the lookback no longer lifts the increase cap.
- The Kubernetes Metrics API collector accepts Go duration windows (`1m30s`, `1h0m0s`, `500ms`) instead of rejecting everything but plain seconds.
- Memory targets rounded up to whole MiB no longer gain a MiB from float noise (900 MiB × 1.1 is 990 MiB, not 991 MiB).
