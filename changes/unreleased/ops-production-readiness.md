### Added

- **Real upgrade test (F17, O1):** `hack/upgrade/upgrade-test.sh` (`make upgrade-test`) installs the 0.3.1 chart and image on a throwaway kind cluster (its own kubeconfig, never the current context), seeds it (`hack/upgrade/seed-v0.3.1.sql`), runs `helm upgrade --reset-then-reuse-values --wait` to the working tree with an image built from it, and asserts api and controller Ready, the schema at the latest migration, every seeded row kept and the API key unchanged and still accepted. The workflow `upgrade-test.yml` runs it on pull requests touching migrations, `db.py`, the chart or the script; `tests/integration/test_upgrade_from_v031.py` runs the same seed against a 0037 schema on PostgreSQL.
- **Release gate (O1, O6):** `release.yml` calls the end-to-end loop (`e2e-nightly.yml`, now `workflow_call`-able) and the upgrade test; nothing is built or published unless both pass.
- **v0.4 exit criterion in the e2e loop:** after the verdict, `hack/e2e/loop.sh` reads `GET /api/v2/changes/{id}/measurements` of the plan's changes and fails when `|measured_allocated - projected_allocated| / projected_allocated` exceeds `E2E_PROJECTION_TOLERANCE` (0.2) for cost; the ratio is recorded in `steps.jsonl` (`projection_accuracy`), and an inconclusive or contaminated measurement is a warning (`hack/e2e/projection-accuracy.jq`).
- **Chart scheduling and availability (N):** per-component `nodeSelector`, `tolerations`, `affinity`, `topologySpreadConstraints`, `priorityClassName`, `podAnnotations` and `podLabels` (`api`, `controller`, `worker`, `renderer`, `postgres`, `postgres.backup`); `global.imagePullSecrets`; PodDisruptionBudgets (`minAvailable: 1`) for the api and the controller with more than one replica; soft pod anti-affinity on `kubernetes.io/hostname` by default for multi-replica components (`podAntiAffinity: soft | hard | none`).
- **PostgreSQL backups:** optional `postgres.backup` CronJob (`pg_dump --format=custom` of the GreenKube schema, checked with `pg_restore --list`, `keep` rotation, own claim kept by `helm uninstall`, Pod Security `restricted`), and the guide `docs/operations/backup-restore.md` (scheduled, off-cluster and manual backups, restore, ledger chain verification after a restore, rollback after migrations = restore, not `helm rollback`). The install notes remind to back up before every upgrade.
- **Operations alerts:** PrometheusRule group `greenkube.operations` (`monitoring.prometheusRule.operations`): `GreenKubeAPIDown`, `GreenKubeDatabaseUnavailable` (controller heartbeat writes failing), `GreenKubeAPIUnavailable`, `GreenKubePostgresDown`, `GreenKubeBackupMissing`, `GreenKubeDataVolumeLow` and `GreenKubeDataVolumeFillingUp` (kubelet volume stats of the data and backup claims), with promtool unit tests.
- **Docs:** production checklist, sizing (database size per 100 pods per year, volume expansion, aggregated retention decision) in `docs/installation.md`; a mandatory "back up first" step in `docs/upgrading.md`.

### Changed

- **Controller rollouts:** the controller and the worker use the `Recreate` strategy (`controller.strategy`, `worker.strategy`), so the old and the new release never write side by side while the schema migrates.
- **Controller Lease hand-over:** a stopping leader releases the Lease (holder cleared, CAS on the resource version), so a standby takes over at once instead of after the Lease duration; in-flight leader work already fails its fence.
- **Pinned helper images:** `postgres:18-alpine` and `busybox:1.37` (init container and Helm test pod, which used `busybox:1.36`) are pinned by their multi-arch index digest; an explicit `digest` key pins any tag.
- **PostgreSQL pod:** memory-backed `/dev/shm` (`postgres.shmSizeLimit`, 128Mi) for parallel query workers and a 60 s termination grace period.
- **Nightly e2e:** the scheduled run checks out `dev` (GitHub only schedules the default branch's workflow), and pull requests touching `src/greenkube/**`, `helm-chart/**`, `frontend/**` or the Dockerfile run the loop.
- **Aggregated metrics retention** stays unbounded by default (documented decision: a finite default would delete existing history at upgrade); `docs/installation.md#sizing` recommends a bound for large clusters.

### Fixed

- **Upgrade crash loop on large databases:** PostgreSQL migrations ran on a pooled connection that inherits `statement_timeout = DB_STATEMENT_TIMEOUT_MS` (30 s), in one transaction, so a backfill longer than that (0039 rewrites the metrics tables) was cancelled and rolled back at every controller start. Migrations now run with `SET LOCAL statement_timeout = 0`, wait without bound for another replica's advisory lock, and use a bounded `lock_timeout` (60 s) for table locks, with an explicit log when it expires.
- **Controller killed while migrating:** the controller's `/healthz` listener started only after the migrations, so a migration longer than the startup probe budget (10 minutes) got the pod restarted mid-migration. The listener now starts first; `/readyz` stays not-ready until the loops start.
- **Slow start after a PostgreSQL restart:** the `wait-for-postgres` init container probed without a timeout, so a SYN dropped while the database pod was replaced stalled it for the kernel TCP timeout (about 2 minutes, seen in the kind upgrade test); each probe is now bounded to 2 s.
