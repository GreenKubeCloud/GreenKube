### Added

- **Action framework (H0a):** a registry of action kinds in `greenkube.automation.actions`. An `ActionKindSpec` declares its kind, typed operation, capability, risk class and measurement strategy, and implements how recommendations become actions, target and invariant validation, compilation to primitive edits, renderer support, the pre-apply baseline it needs, no-op detection, apply detection, the baseline-derived inverse, policy fields and its PR section. Registering a kind also registers its operation with `ActionPlanV3`, so persisted plans parse it without contract changes. `container_resources` (`set_container_resources`) is the built-in kind; a test-only kind defined outside `src/` is planned end to end through the raw and Kustomize strategies to prove a new kind needs no change elsewhere.
- **Primitive operations and patch strategies (H0b):** `SetField`, `RemoveField`, `CreateResource` and `DeleteResource` with JSON-pointer-like paths whose `[name=…]` selectors address list entries the strategic-merge way. The raw, Kustomize, Helm values and Flux HelmRelease planners are `PatchStrategy` implementations (`renderer_kind`, `supports`, `plan`). The raw and Kustomize planners apply compiled primitives; the Kustomize managed patch is generated from the primitives and merged with the fields an earlier managed patch already sets, and every field of a managed patch must be owned by a registered kind. The Helm planners express container-resource fields only (the values planner answers `needs_mapping` until the container has an explicit values mapping), validate actions through the registry and reject non-container kinds with an explanation. No strategy creates or deletes resources yet: those primitives are refused before planning.
- **Generic expected-delta render validation (H0c):** a rendered result must equal the rendered source before the edit changed by exactly the kind's expected delta (field changes, created and deleted resources), with the kind's invariants (request ≤ limit for container resources) checked on the expected and rendered result. The validator accepts the resources a kind declares it creates or deletes, ready for kinds whose strategies can place them.
- **Resource bindings by GVK and name (H0d):** `ResourceBindingIndex` (`greenkube.gitops.discovery.inventory`) maps Argo CD `status.resources` and Flux `status.inventory` entries (including cluster-scoped ones) to the controller that manages any resource and its resolved Git location. Resources listed by several controllers are ambiguous and unlisted ones unmanaged; `bind_resources` fails closed on both.

### Changed

- Planners, the plan worker (no-effective-change check, pre-apply baseline capture and validation, rollback review), rollback (HELM_VALUES inverse, Flux HelmRelease inverse scope), apply detection, plan runtime and policy gates ask the action kind instead of testing `SetContainerResources`. Rendered plans are byte-identical before and after (golden plans for raw, Kustomize including Flux `targetNamespace`/`namePrefix` and namespace-less Argo CD overlays, Helm values, Flux HelmRelease and raw/Kustomize rollback).
- The published `ActionPlanV3` schema keeps the discriminated union of typed operations (`SetContainerResources`, `DeleteResource`, `AddHorizontalPodAutoscaler`) and accepts the plain objects of registered kinds.
- Unsupported operations are reported with the list of supported action kinds ("only per-container rightsizing operations are supported").

### Fixed

- **D14 follow-up:** Kustomize and raw-manifest rollback render validation accepts the namespace-less Argo CD target that forward planning allows (the controller supplies the destination namespace), instead of failing with "rollback render did not preserve the original exact resource target".
