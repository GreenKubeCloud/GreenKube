### Added
- **Controller loop registry (M8).** Every periodic job of `greenkube start` is declared once in `LoopRegistry` (`greenkube.core.loops`): name, interval, jitter, leader-only flag, timeout, backoff. Leader-only ticks run only on the Lease holder, inside a `LeaderFence` scope. Each loop has its own task: a failing or timed-out tick does not stop the others, and a crashed loop task is restarted. Loops: `collection`, `carbon-intensity`, `node-analysis`, `savings-attribution`, `recommendation-lifecycle`, `recommendation-scan`, `metrics-compression`, `dashboard-summary`, `gitops-discovery`, `gitops-sync`, `automation-controller`, `plan-executor`, `session-purge`.
- **Loop metrics (M8).** `greenkube_loop_runs_total{loop,outcome}` (success, failure, timeout, skipped), `greenkube_loop_duration_seconds{loop}`, `greenkube_loop_last_success_timestamp_seconds{loop}`, `greenkube_loop_consecutive_failures{loop}` and `greenkube_controller_leader`, served by the controller metrics endpoint. Jobs that log and swallow their own errors now mark their tick failed through `report_loop_failure()`; such reported failures are counted but never back off, so every job keeps its previous cadence. Only ticks that raise or time out back off.
- **Controller health endpoints (M8).** On `CONTROLLER_METRICS_PORT` the controller now serves `/healthz`, `/readyz` (`503` when a loop task died or its heartbeat is stale) and `/loops`, a per-loop JSON snapshot that requires the API key when the controller has one.
- **Automation controller loop (M8, F8).** One leader-gated controller loop (`greenkube.automation.controller`) runs, under a single database lease (the singleton `gitops_pr_polling_lease` row): webhook outbox reconciliation, PR polling and branch cleanup, pending-PR recovery, exhausted-operation reconciliation, plan expiry (every 60 s) and automation history retention (daily). The DB lease keeps that work to one process even without Kubernetes leader election.

### Changed
- **Process topology (M8, F8).** The API is now stateless request handling: it starts no worker, no plan expiry sweep and no session purge, so API replicas are safe to scale. Plan execution runs in the controller (`plan-executor` loop) whenever automation is enabled. `automation.mode=worker` adds dedicated worker pods as extra executors. `inline` means the controller is the only executor.
- **Optional worker (F8).** `python -m greenkube.cli.automation_worker` only claims and executes plan operations. The webhook outbox, PR polling, branch cleanup, pending-PR recovery and heartbeat retention moved to the controller. `production.components.automation.replicas` is honoured, with at least 1 in worker mode; operation leases make several executors safe.
- **Helm.** The controller container (standalone) and Deployment (production) receive `AUTOMATION_ENABLED`/`AUTOMATION_MODE` whenever automation is enabled, in either mode, and mount the Git provider credentials. The profile values are unchanged until F11.
- The automation controller loop takes the database lease only when one of its steps is due, and a standby controller resets `greenkube_automation_worker_up` to 0.
- The session purge (F14) moved from every API replica to the controller's `session-purge` loop.
- GitOps discovery and sync runtimes expose `run_once()`, which the registry schedules; their `run_periodic()`/`run()` loops are kept for embedders.

### Removed
- The plan expiry, exhausted-operation reconciliation and retention sweep that ran in every API replica (`api/startup.py:run_plan_expiry_loop`, BUG-57), and the inline plan worker started by the API lifespan (`AUTOMATION_MODE=inline` in the API).
