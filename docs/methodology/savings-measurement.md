# Savings measurement — methodology

**Strategy:** `request_rightsizing` version `2.5` (`greenkube.verify.strategy.RequestRightsizingStrategy`) · **Code:** `src/greenkube/verify/` · **Roadmap:** C1–C9, N9

GreenKube measures every applied change once, against a counterfactual: what the workload would have cost **without** the change. The method follows the spirit of IPMVP Option B (retrofit isolation with measurement of the affected system): a baseline period before the change, a reporting period after it, a model that adjusts the baseline to the reporting period's conditions, and an uncertainty statement.

This page is the reference for reviewing and auditing a measurement. When a rule below changes the numbers a measurement produces, the strategy version must change.

Recommendations marked applied by hand (`PATCH /api/v1/recommendations/{id}/apply`) are recorded as changes too (application method `manual`, MEA-16): the endpoint stores a change id on the recommendation, records the change and freezes its baseline snapshot, and the lifecycle job's repair records it later if that fails, so the interim verifier never judges them. Applied, undecided recommendations without a change id (applied before change measurement shipped) are adopted on the next lifecycle pass: their records get a change id (`baseline.change_adopted_at` records when) and the change is recorded like any other. Only with `CHANGE_MEASUREMENT_ENABLED=false` (and for a record whose window the interim verifier closed in the same pass, before the adoption) does the interim verifier described in [recommendation.md](../recommendation.md#lifecycle-states) still decide.

**The interim verifier is not covered by this document's statistics.** Since strategy `c0.2` (MEA-16) it no longer decides on a point estimate: it computes the 90% interval of the baseline-minus-after rate delta (circular block bootstrap with one-hour blocks of the per-sample rates of each window, Welch degrees of freedom) and uses the same rule as change measurement: `realized` when the interval lies above the noise floor (2% of the baseline rate, `MIN_RELATIVE_CHANGE`), `not_realized` when it lies at or below it, `inconclusive` when it straddles it (reason "straddles the noise floor", no window extension) or when a window has fewer than two samples. The interval only sees within-window noise: there is still no counterfactual, no between-week term and no confounder check, so a week-level shift or a price move can still be booked there. Its measurements carry `windows.method = interim_before_after` and the interval in `estimates[].ci_low_per_hour`/`ci_high_per_hour`; rows decided with `c0.1` keep their point-estimate verdicts. Installs that run with `CHANGE_MEASUREMENT_ENABLED=false` get these weaker verdicts; their decisions are the rows of the `savings_measurements` table, not `change_measurements`. The savings totals do not yet report interim-method amounts in a separate block.

## Vocabulary

| Term | Meaning |
|---|---|
| **Change** | One pod-template revision rolled out on one workload: a GitOps plan merged and synced, or a change detected in the cluster. Several recommendations (the CPU and memory requests of one or more containers) can belong to one change. |
| **Baseline window** | The period before the change used to predict the counterfactual. |
| **Post-window** | The period after the change in which the saving is measured. |
| **Counterfactual** | The predicted value of a quantity in a post-window hour had the change not been made. |
| **Saving** | Counterfactual minus actual, per hour. Signed: a negative saving is a cost increase. |
| **Measured** | A saving from this method. It is never added to a **projected** saving (the [Impact Model](impact-model.md) estimate made before the change). |

## 1. Recording the change (C1)

Apply detection reads every Deployment, StatefulSet and DaemonSet on each lifecycle pass. For each workload it records a **spec observation** whenever its UID, generation, pod-template digest or HPA digest differs from the previous one. The pod-template digest is the SHA-256 of the canonical JSON of the pod template, with empty fields removed and the `pod-template-hash` label ignored. When HPAs cannot be listed in a pass, the last known HPA digest is kept, so a failed listing is not recorded as an HPA change.

Next to it, each observation and each change record two narrower digests (MEA-08, migration 0136): the **resources digest** (SHA-256 of the requests and limits of every container, init container and native sidecar, plus pod-level `resources`) and the **image digest** (SHA-256 of the containers' images). A measured saving depends on the requests only (allocated cost is requests × unit price), so these digests decide whether a later template change touches it: an image deployment, an env change or a `kubectl rollout restart` changes the pod-template digest but not the resources digest. Observations and changes stored before 0136 have no resources digest (`NULL`); the first pass after the upgrade records one new observation per workload with them.

When a recommendation is detected as applied (its rollout has completed and the live requests match the proposal), GreenKube records one immutable **change** per plan and workload revision:

| Field | Source |
|---|---|
| `recommendation_ids` | Every recommendation applied by that revision (members detected in a later pass are appended). |
| `plan_id`, `pr_url`, `merge_sha`, `gitops_revision`, `synced_at` | The GitOps plan and its pull request, when the change came through a pull request. |
| `workload_uid`, `generation_before/after`, `spec_digest_before/after` | The live workload and the last observation of a different revision (or the plan's pre-apply baseline for the generation). `details.spec_before_source` says which. |
| `rollout_started_at` | The first observation of the new revision, else the sync time, else the completion time (`rollout_started_source`). |
| `rollout_completed_at` | Every replica updated and available (`rollout_completed_source`: the Deployment `Progressing` condition, otherwise the detection time). |
| `baseline_window_end` | The PR merge (the Git provider's merge time), otherwise the plan approval, otherwise the rollout completion. |

At the same time GreenKube freezes a **baseline snapshot**: the workload's hourly observations over the baseline window, the load-driver series available for that window, the unit prices observed in it, the dominant carbon-intensity source and the Impact Model version. The snapshot carries a `content_sha256` over its content; `GET /api/v2/changes/{id}` reports whether it still verifies. Measurements always use the frozen snapshot, never a re-read of the baseline period.

Evidence is never frozen from a failed read. When the metrics of the baseline window cannot be read (a database error or timeout), no snapshot is written and the change stays `applied`; the next lifecycle pass retries. When a Prometheus load-driver query fails (as opposed to returning no series), the snapshot waits for Prometheus for up to 24 hours after the change was recorded; after that it is frozen without that driver and lists it in `collector_versions.load_drivers_unavailable`.

## 2. Windows

| Window | Definition |
|---|---|
| Baseline | `[baseline_window_end − CHANGE_MEASUREMENT_PRE_WINDOW_DAYS, baseline_window_end)`, 7 days by default. It ends at the merge or approval, so it never contains the change. |
| Post | `[rollout_completed_at + CHANGE_MEASUREMENT_WARMUP_HOURS, + CHANGE_MEASUREMENT_POST_WINDOW_DAYS)`, 1 hour of warm-up and 7 days by default. At least 5 days (a verdict needs 5 complete days of aligned hours, MEA-10): a shorter post-window is raised to 5 days at startup with a warning (never a startup failure), unless `CHANGE_MEASUREMENT_ACCELERATED` is on (then at least 30 minutes). |
| Interim health | `[post start, post start + VERIFICATION_WINDOW_HOURS)`, 72 hours by default. |

Seven days give every hour of the week one baseline observation. A shorter baseline leaves hours of the week unmatched, which lowers coverage (section 4).

## 3. Hourly observations

Rows of the workload (pod level, all containers) are reduced to one bucket per UTC clock hour:

- **Allocated cost** — only from rows whose cost provenance is trusted (`opencost`, `opencost_derived`, `kubecost`, `pricing_catalog`; or, for legacy rows, a positive cost not flagged estimated). A sample time counts only when every replica row at that time is trusted. The rate divides by the covered time. Hourly rollup rows (one per pod and hour, read for the part of a window older than the compression watermark) carry each pod's first and last sample and the cost, CPU and RAM cost and pod-seconds of its trusted samples: the covered time of an hour is the union of the pods' sample spans (a rollout hour is not inflated by the longest pod), and one untrusted sample removes only its own time, so an hour gives the same bucket before and after compression. Rollup rows written before this change have no sample bounds: an hour where several pods each covered part of it is left out rather than inflated. A missing cost is missing, never zero: an OpenCost allocation whose `totalCost`, `cpuCost` or `ramCost` is NaN, infinite or absent (with no CPU and RAM cost to rebuild the total), or whose total is 0 for a pod that ran (`minutes > 0`) with non-zero requests, is stored with `cost_source = none` and the default placeholder cost, and a stored row with a zero total and non-zero requests is not trusted either. Such hours do not count; they never read as the whole cost saved. A zero that is only OpenCost's 5-decimal rounding (a small pod over a one-minute step) is not missing: its cost is rebuilt from its resource-hours at OpenCost's node unit prices and stored as `opencost_derived` (see [OpenCost precision](impact-model.md#opencost-precision-sub-precision-costs)).
- **CPU and RAM cost components** (`cost_cpu`, `cost_ram`) when every trusted row carries them.
- **Requested capacity** — requested CPU cores and memory GiB summed over replicas.
- **Charged capacity** (`charged_core_hours`, `charged_gib_hours`, MEA-02) — `max(request, usage)` per sample, summed over replicas: the quantity OpenCost charges. A sample without trusted usage counts its request. Hourly rollup rows carry a mean usage, so their charged quantity is `max(request, mean usage)`, a lower bound when usage peaked above the request inside the hour. Snapshots frozen before it was measured have no value for it (absent from their hours and digest).
- **Replicas** — the mean number of pods covering the hour (pod-seconds over covered seconds).
- **CPU usage**, **energy**, **CO₂e** (only from rows with measured intensity and a profiled node), and the node **instance types** running the pods.
- **Embodied CO₂e** (`embodied_co2e_grams`, the hardware manufacturing emissions the Impact Model allocates by reservation). It does not depend on the grid intensity, so it needs no measured intensity. Snapshots frozen before it was measured have no value for it (`embodied_co2e_g` is absent from their hours and from their digest, which therefore still verifies).
- **Carbon factor** (`carbon_factor`, MEA-03) — the time-weighted grid intensity × PUE of the hour's trusted-carbon rows (rows with a positive intensity and PUE), in gCO₂e/kWh, independent of energy. Absent from snapshots frozen before it was recorded (and from their digest).

An hour counts for a quantity when at least half of it is covered by qualifying data.

### Constant prices (version 2.4, MEA-02)

A request change moves the charged quantity, not the price. Before 2.4 the claimed `allocated_cost` was the difference of the stored costs, each valued at the prices of its own window, so a price move between the windows (spot prices, a reserved-instance or custom-pricing edit) was booked as a saving or erased one: in the audit simulation a true saving of 175.32/yr was measured as 227.92/yr after a 30% price cut and 122.72/yr after a 30% rise, with no confounder on clusters without node-pool labels.

Since 2.4, every hour of both windows is revalued before the counterfactual is fitted:

- CPU cost = charged core-hours × the baseline CPU price per charged core-hour, RAM cost = charged GiB-hours × the baseline memory price per charged GiB-hour; any other cost component (GPU, storage: total − CPU − RAM) is kept as observed. `allocated_cost`, `cost_cpu` and `cost_ram` are these constant-price values.
- The prices are the frozen baseline snapshot's `price_card` (`cpu_charged_core_hour`, `memory_charged_gib_hour`: trusted CPU and RAM cost of the baseline hours over their charged quantities). Valuing the **charged** quantity, not the request, keeps usage-driven allocation: when a request is cut below the usage, OpenCost keeps charging the usage, and so does the measurement (no phantom saving).
- Snapshots frozen before the charged quantities were measured get them derived for every hour without them: `charged_core_hours = max(core_hours, cpu_usage_cores)` (the hourly mean usage, a lower bound of the per-sample maximum) and `charged_gib_hours = gib_hours` (memory usage is not in the buckets), recorded as `constant_price_basis = charged_derived`. They are priced at the card's charged prices when it has them, else at the prices of the derived baseline hours (`constant_price_source = baseline_hours`), else at the card's per-request prices (`snapshot_price_card_requested`). Valuing the request instead booked a saving the allocator never gave when the request was cut below the usage: 1.0 → 0.5 core with 0.8 core used after claimed 0.0200/h for a true 0.0110/h (second review wp07-2). Only windows without CPU usage to derive from keep the requested quantity and the per-request prices (`constant_price_basis = requested`). Without any baseline price (no CPU/RAM cost components) the observed cost is measured, recorded as `constant_price_basis = observed`, with a moderate `constant_prices_unavailable` confounder. An hour without cost components or quantities is not measured (lower coverage).
- The cost at the observed prices is reported as a second quantity, `allocated_cost_observed` (not claimed), and `counterfactual_params.price_effect` = observed saving − constant-price saving. `counterfactual_params` also records `constant_price_basis`, `constant_prices` and `constant_price_source` (`snapshot_price_card`, or `baseline_hours` when no card was passed).

### CO₂e at the post-window carbon factor (version 2.4, MEA-03)

The stored CO₂e of an hour is its energy × PUE × the grid intensity of that hour. Before 2.4 the claimed CO₂e saving was the raw difference of the two windows' emissions, so a windier or calmer post week was booked as a carbon saving or loss of the change: a real cut from 0.050 to 0.040 kWh/h at 300 g/kWh (3.0 g/h) was measured as 7.0 g/h when the post week averaged 200 g/kWh and as −1.0 g/h at 400 g/kWh.

Since 2.4 the operational CO₂e of every hour of both windows is its energy (`energy_kwh`) × a **post-window carbon factor** (grams of CO₂e per kWh, i.e. grid intensity × PUE as the Impact Model applied them, over the hours whose every sample has trusted carbon): each post hour at **its own** factor, each baseline hour at the post factor of the **same hour of the week** (the time average over the post hours of that hour of the week when the post-window is longer than a week). An hour's factor is the bucket's recorded `carbon_factor` (the time-weighted grid intensity × PUE of its trusted-carbon rows, independent of energy, so an hour with zero energy keeps its factor); snapshots frozen before it was recorded use `co2e_g / energy_kwh` of hours with positive energy. An hour of the week without any post factor (the workload scaled to zero, post hours missing, or an older snapshot's zero-energy hour) falls back to the **plain time average of the post hours' factors** (`co2e_factor_fallback`, not energy-weighted, so the fallback carries no load weighting); `co2e_factor_fallback_share` records the share of the baseline energy valued that way, and above 5% a mild `co2e_factor_fallback` confounder reports it (informative: it touches the CO₂e valuation only, so it costs the cost verdict no confidence). With the hour-of-week counterfactual the claimed saving is therefore `mean over post hours of (E_baseline(how) − E_post(t)) × factor_post(t)`: the energy saving of each hour valued at what the grid emitted per kWh in that hour after the change, plus the embodied delta (embodied CO₂e does not depend on intensity). Only hours with trusted carbon count, as before, so an install without measured intensity still has no CO₂e verdict. `energy_kwh` is reported as its own quantity.

`counterfactual_params` records `co2e_basis` (`energy_delta_at_post_hourly_intensity`), `co2e_factor_pre`, `co2e_factor_post` (energy-weighted window factors), `co2e_factor_fallback`, `co2e_factor_fallback_share` and `co2e_raw_delta` (the pre-2.4 raw mean difference, for comparison). An `intensity_shift` confounder (moderate) reports a window carbon factor that moved more than 10% between the windows, with both values; it is informative and costs no confidence, since the saving is normalised for intensity hour by hour. Without energy behind the post-window CO₂e the raw difference is measured (`co2e_basis = raw_delta`) with a moderate `co2e_raw_delta` confounder.

Deviation from the audit's fix text: the factors are derived from the stored CO₂e and energy instead of new per-hour intensity and PUE fields, so snapshots frozen earlier are measured the same way and need no fallback. An earlier 2.4 build valued every hour at the single energy-weighted post-window factor; that factor is weighted by post-window energy, not by the saving, so a constant 0.01 kWh/h saving with load in phase with intensity (300 ± 100 g/kWh) claimed 3.5 g/h instead of 3.0 (+17%), and 2.5 g/h out of phase (second review wp07-2). Measurements stored by that build keep `co2e_basis = energy_delta_at_post_intensity`; they are not recomputed.

Within-window price variation is removed with the window-level move: hourly cost noise of fixed requests is price noise and no longer widens the interval; variation of the charged quantity (usage above the request, replicas) still does. Measurements decided by 2.3 or earlier keep their observed-price values; they are not recomputed.

## 4. Counterfactual (C3)

### Load driver

The counterfactual is adjusted by a **load driver**, the hourly amount of work the workload was asked to do. GreenKube takes the first candidate whose coverage is at least `CHANGE_MEASUREMENT_MIN_COVERAGE` in both windows and whose baseline is not all zero:

1. requests per second from the service mesh or ingress: Istio `istio_requests_total{reporter="destination"}`, Linkerd `response_total{direction="inbound"}`, ingress-nginx `nginx_ingress_controller_requests` for a Service named after the workload, then Envoy `envoy_cluster_upstream_rq_total` for Contour-style clusters (`<namespace>_<service>_<port>`) of a Service named after the workload;
2. the PromQL expression in the workload annotation `greenkube.io/load-metric` (`$namespace` and `$workload` are substituted);
3. the workload's CPU usage from GreenKube's metrics. It is the weakest driver (a CPU change can move it) and is flagged `weak`.

Prometheus drivers are read as hourly means (`avg_over_time((<expr>)[1h:5m])` with a one-hour step). Without Prometheus only the CPU-usage driver is available.

### Load regression (C3 v2)

When a load driver exists, each quantity is first modelled by ordinary least squares on the baseline window (`greenkube.verify.regression`):

```
metric(t) = α[slot(t)] + β × load(t) + ε(t)
counterfactual(t) = α[slot(t)] + β × load(t)        for each post-window hour
```

`slot(t)` is the **hour of the week** when the baseline holds at least two observations of 90% of the 168 hours of the week (a 14-day baseline or more); otherwise the **hour of the day split into weekdays and weekends** (48 slots). With the default 7-day baseline every hour of the week is seen once, so hour-of-week dummies would absorb every observation and leave `β` unidentifiable. Because the slots partition the hours, the fit has a closed form: `β` is the slope of the within-slot demeaned metric on the within-slot demeaned load, and `α[s]` the slot mean minus `β` times the slot's mean load.

The fit is used only when its **diagnostics** pass, otherwise the quantity falls back to the hour-of-week model below (`methods[quantity] = hour_of_week_mean`, `diagnostics[quantity].fallback`):

| Diagnostic | Failure |
|---|---|
| Paired baseline hours (value and load) | fewer than 48 |
| Residual degrees of freedom (hours − slots − 1) | fewer than 24 |
| Within-slot load variation | none: `β` is not identifiable |
| Sign of `β` | negative with t < −2: the load does not explain the metric |
| Extrapolation | more than 20% of the post-window hours have a load outside the baseline range widened by 25% |

The measurement records, per quantity, the method (`ols_load_seasonal` or `hour_of_week_mean`) and the diagnostics: seasonality, observations, slots, degrees of freedom, R² and adjusted R², residual standard deviation, `β` with its standard error and t-statistic, the Durbin-Watson statistic of the residuals, the extrapolated share and the failures. `counterfactual_params.model` is the method of `allocated_cost`.

### Hour-of-week model (C3 MVP, fallback)

For each post-window hour `t` with hour of the week `h`:

```
counterfactual(t) = mean_baseline[h] × (load(t) / load_baseline[h]) ^ β
saving(t)         = counterfactual(t) − actual(t)
```

`β` is the **load elasticity** of the quantity, fitted on the baseline window as the least-squares slope of `log(quantity)` on `log(load)`, clamped to `[0, 1]`. It is 0 when fewer than 24 baseline hours pair a positive value with a positive load, or when the load hardly varies.

- An autoscaled workload, whose replicas follow its traffic, gets `β ≈ 1`: twice the traffic, twice the expected cost.
- A fixed-capacity workload, whose requests do not move with traffic, gets `β ≈ 0` and its counterfactual is not rescaled. Scaling it by the raw load ratio would credit any traffic growth as a saving (the defect behind BUG-27).

A post-window hour is **aligned** when it has a value and its hour of the week has a baseline mean (and, when `β > 0`, a load value). **Coverage** is the number of aligned hours divided by the number of hours in the post-window.

The fitted elasticities and the number of matched hours of the week are stored in the measurement as `counterfactual_params`. Without a load driver this model is used with `β = 0` (no diagnostics are recorded).

## 5. Quantities

The `request_rightsizing` strategy (version 2.5) measures, per hour:

**Per replica.** A request change moves what each replica is charged, not how many replicas run. Every quantity below is fitted *per replica* (each hour's value over its replica count) and the per-replica saving is multiplied by the mean replica count of the aligned post-window hours: `saving = Δ(per-replica rate) × post replica-hours`, which is `Σ Δrequest × replica-hours` for requested capacity. A replica count that drops for another reason (an HPA scaling 4 → 2 during the post-window) is therefore never credited to the change: it saves nothing per replica. It is reported by the `replica_shift` confounder (moderate). Hours without a replica count are left out. The interval and counterfactual are scaled by the same replica count, so the outcome rule decides exactly as it would per replica. Measurements decided by version 2.0 compared workload totals (stated by `strategy_version`).

**Both bases, the smaller claim (2.2).** Per-replica scaling alone fails in the mirror direction: a CPU-request cut that makes an HPA scale out (2 pods at $0.01/h → 4 pods at $0.005/h) halves the per-pod cost while the workload total stays $0.02/h, and per-replica scaling would credit $0.02/h. Every quantity is therefore fitted twice, per replica and on workload totals, and the estimate with the **smaller mean saving** is kept; it stays `realized` only when both bases are realized, otherwise it is `inconclusive` with the reason. A replica drop (the per-replica basis is smaller) and a replica rise the change caused (the workload total is smaller) are both left out, so neither direction is credited. The basis kept for each quantity is recorded in `counterfactual_params.replica_basis` (`per_replica` or `workload_total`). Measurements decided by version 2.1 used the per-replica basis alone.

| Quantity | Unit | Claimed | Role |
|---|---|---|---|
| `allocated_cost` | currency | yes | Decides the outcome. At the baseline unit prices since 2.4 ([constant prices](#constant-prices-version-24-mea-02)). |
| `allocated_cost_observed` | currency | no | The allocated cost at the prices of each window, as stored (reported; `price_effect` = its saving − the `allocated_cost` saving). |
| `cost_cpu`, `cost_ram` | currency | no | At the baseline unit prices; split the saving between the change's recommendations. |
| `core_hours`, `gib_hours` | core-hours, GiB-hours | no | Requested capacity freed. |
| `co2e_g` | gCO₂e | yes | CO₂e as the Impact Model allocates it: operational (idle and memory power follow the reservation) plus embodied (allocated by reservation) when both windows measured it. Claimed when the change is realized and its own interval shows a saving; compared with the projection of the same components only ([component matching](impact-model.md#co2e-components-and-component-matched-comparison)), listed in the estimate's `components` and in `counterfactual_params.co2e_components`. Split between the change's recommendations by their projections of those components. |
| `embodied_co2e_g` | gCO₂e | no | The embodied part alone (reported). |
| `energy_kwh` | kWh | no | Energy of the workload; since 2.4 the basis of the operational CO₂e saving ([CO₂e at the post-window carbon factor](#co2e-at-the-post-window-carbon-factor-version-24-mea-03)). |

Stored rows are allocated by the Impact Model: idle CPU power follows the CPU reservation, memory power the memory reservation and embodied emissions the CPU reservation, so a request change moves the measured CO₂e. A baseline snapshot frozen before embodied emissions were measured carries none; its measurement compares operational CO₂e with the operational projection, as before (`components = [operational_energy, idle_share]`). A window whose embodied CO₂e is zero everywhere (no hardware profile for its nodes) is treated the same way. Before Impact Model 2.0.0, `co2e_g` was reported only and recommendations stored a measured CO₂e of 0.

### Released capacity and the capacity verdict (WP-08.1)

The `core_hours` and `gib_hours` quantities above come from the request columns of the metric rows, which are wrong for replaced pods. Every decided measurement therefore also carries `capacity` (`greenkube.verify.capacity`, version `capacity/1`), measured from the workload specs alone:

- **Requests.** The applied detector records the per-container requests and limits with each workload spec observation (`workload_spec_observations.container_resources`, migration 0140). *Before* is the latest observation of the change's `spec_digest_before` recorded before the rollout completed, else the latest observation recorded before the rollout started (never the merge time: for a manual apply the baseline ends at the rollout completion, after the new revision was first seen); *after* is the latest observation recorded after it and before the post-window end, or the *before* spec when no new revision was observed. Only containers present before and after are compared (`containers_removed` and `containers_added` list the others: a removed container is not a release), and classic init containers are left out (native sidecars are kept). `requests_source` says which was used (`spec_observation`, `spec_observation_unchanged`, `change_record` for the requests recorded with the change, or `missing`).
- **Per replica and in total.** `per_replica` = requested cores and GiB per replica before minus after (summed over the change's containers); `replicas` = the mean replica count of the baseline and post-window hour buckets; `total` = `per_replica ×` the baseline replicas (the request effect); `net` = requested capacity before minus after; `cpu_core_hours` / `mem_gib_hours` = `total ×` the covered post-window hours.
- **Replica change.** When the mean replica count moved by 0.5 or more, `replica_change` reports it (before, after, and the capacity that move reserved at the new request, negative for a scale-out), so that `total + replica_change = net`. It is never booked as a release.
- **Verdict.** `released` when at least 90% of the per-replica decrease the recommendations proposed (current minus applied or proposed request) is observed for every resource they changed, `not_released` below 5%, `partially_released` in between. Without a proposal a decrease is `released`. `unknown` when the requests before or after were not recorded (changes measured before migration 0140). An increase gets no verdict (`direction: increase`): more capacity reserved is never a release.

The capacity verdict never reads a price or the cost outcome: it is decided when the cost verdict is `inconclusive`, on a cluster without OpenCost and without an autoscaler. Released capacity is never converted to money and never added to cost savings. It is returned by `GET /api/v2/changes/{id}/measurements` (`capacity`, `method: measured`, with units) and shown on the change page. It is not accrued in the savings ledger yet: the ledger (WP-09) books `cost` and `co2e_g` only.

### Resource deletions (`resource_deletion` 1.1, H6)

Deleting an orphaned LoadBalancer Service or PersistentVolume releases the asset's whole allocated rate once apply detection has verified that the resource is absent. The rate is the mean trusted cost of the resource in the baseline window when GreenKube observed it (`pre_window_mean`, rate source `observed`), otherwise the rate frozen in the recommendation's projection (`allocated_rate_at_decision`), **only when that rate has a trusted provenance**: the OpenCost or Kubecost per-asset cost or a pricing-catalog asset price (`impact.assumptions.cost_source`). A configured default (`LOAD_BALANCER_COST_PER_MONTH`, `STORAGE_COST_PER_GIB_MONTH`, recorded as `custom_rate`), no cost (`none`), recommendations that disagree (`mixed`) or an unknown provenance are never booked as measured: the deletion is `inconclusive` with the reason, and its saving stays a projection. The rate source is recorded on the estimate (`rate_source`), in `counterfactual_params.rate_source` and in the measurement's `strategy_version` (`1.1:<method>:<rate source>`, e.g. `1.1:allocated_rate_at_decision:opencost`), which the savings ledger v2 carries as its entries' `method_version` (`resource_deletion/1.1:…`). A resource still observed after the change is `not_realized`, a deletion whose absence was never verified is `inconclusive`.

## 6. Uncertainty and outcome (C4)

### Interval (version 2.3, MEA-01)

The interval of the mean hourly saving has two variance terms.

**Within the windows.** The hourly savings of the aligned post-window hours, in time order, are resampled with a **circular block bootstrap**: blocks of 24 consecutive hours (one day) start at any hour and wrap around the end of the series, so every hour is drawn equally often, and are concatenated to the series length. `CHANGE_MEASUREMENT_BOOTSTRAP_SAMPLES` resamples (1000 by default) give the distribution of the mean. Its standard deviation is the within-window standard error, multiplied by `√(b / (b − 1))` for the `b` day blocks of the series (the bootstrap divides by `b`, which understates the variance with 7 blocks); it carries `b − 1` degrees of freedom. Day blocks keep the within-day correlation of the savings, which resampling single hours would ignore.

With the load regression, each resample also adds a **residual bootstrap** of the baseline. The baseline residuals, inflated by `√(n / dof)`, are resampled in the same circular one-day blocks; refitting on the fitted values plus those residuals moves the counterfactual of every aligned post-window hour, and the mean saving with it. The move is linear in the residuals (slot means move by their slot's mean residual, `β` by `Σ dx·e / Sxx`), so it is computed with one weight per baseline hour instead of a refit.

**Between weeks.** Anything that moves the level of a whole week (traffic, a replica level, a spot or reserved price, grid intensity, a holiday) is a constant offset in every hourly saving of that week, which no resampling inside the windows can see. Before 2.3 such a shift was read as a certain effect: with a true saving of zero, a 5% week-to-week level variation produced `realized` in half of the simulated changes. Its variance is `σ_w² × (1/K + 1/P)`, for `K` complete baseline weeks (at least 84 of their 168 hours, counted back from the baseline end) and `P = max(1, aligned post hours / 168)` post weeks:

- with **`K ≥ 2`** (`CHANGE_MEASUREMENT_PRE_WINDOW_DAYS` ≥ 14), `σ_w` is the sample standard deviation of the weekly mean residuals of the baseline (each hour minus its fitted counterfactual), with `K − 1` degrees of freedom. Those weekly means already carry the within-week noise the bootstrap measures, so only the excess of the between-week variance over the within-window variance is added (a method-of-moments split; the noise is not counted twice);
- with **`K < 2`** (the default 7-day baseline), the weekly level cannot be estimated, and `σ_w = CHANGE_MEASUREMENT_PRIOR_WEEK_CV × |mean counterfactual|` (5% by default), taken as known (infinite degrees of freedom). Exception: a **deterministic** baseline (relative standard deviation of the hourly values at most 10⁻⁴, e.g. fixed requests on fixed-price nodes; the tolerance absorbs float noise and price-feed rounding, so an exactly flat series and the same series with 10⁻⁶ jitter get the same verdict) gets no between-week term: its level is set by configuration, whose changes the price and pool confounders report.

  The exemption is a threshold, so the verdict switches at it: at a relative noise of 10⁻⁴ the between-week prior goes from "not applied" (`between_week_basis = deterministic_baseline`) to "applied" (`prior`). In the second review's simulation (wp07-2, a 7-day flat baseline and a 10% saving, 50 seeds per level) relative hourly noise up to 5·10⁻⁵ gave `realized` every time, 9·10⁻⁵ gave 96% `realized`, and 1.2·10⁻⁴ or more gave `inconclusive` every time: just above the threshold the 5% prior is added and a 10% saving no longer clears the floor with one baseline week. This step is kept on purpose: a level set by configuration has no week-to-week variation to estimate, and any real usage variation is far above 10⁻⁴. A 14-day baseline estimates the weekly level instead of assuming it.

The interval is `mean ± t(0.95, ν) × √(se_within² + se_between²)`, with `ν` from the Welch-Satterthwaite formula. A deterministic series (constant before, constant lower after) keeps a zero-width interval.

**Assumptions.** Week-level shifts are independent between weeks and of the change (no trend); hourly savings are stationary within the windows, with correlations shorter than a day; with one baseline week, the prior is an upper bound of the true week-to-week variation of the quantity (5% is the order observed for HPA-scaled cost and is lower than typical weekly grid-intensity moves, so CO₂e verdicts with a 7-day baseline are optimistic). A longer baseline replaces the prior by an estimate; the default stays 7 days until hourly rollup rows (older than the raw retention) give exact hour buckets.

**Validated rates.** `tests/verify/test_verdict_validity.py` runs the real fit on seeded synthetic series (400 trials, true saving 0, 7-day post window). Observed false-`realized` rates with the noise floor: independent hourly noise 0% (7-day baseline) and 0% (28-day), AR(1) φ = 0.9 0% and 1.0%, a 5% week-level shift 2.5% and 3.0%. Without the noise floor (the interval alone, nominal one-sided rate 5%): 3.7% for the week-level shift with the prior, and 1.3% / 2.8% / 5.0% for independent, AR(1) and week-level noise with a 28-day baseline. A true 30% saving with a 5% week-level shift is `realized` in 100% (7-day) and 98.8% (28-day) of trials; a 10% saving in about 28% (the price of the between-week term with one baseline week).

**Known limitation: one baseline week (the default).** The 5% prior is only valid when the true week-to-week variation of the quantity is at most 5%. When it is larger, the interval is too narrow and a zero saving is declared `realized` more often than the nominal 5%. The review simulation (400 trials, true saving 0, noise floor on) measured false-`realized` rates of 0%, 2.0%, 16.0% and 33.5% for a week-to-week coefficient of variation of 2%, 5%, 10% and 20% with a 7-day baseline, against 1.2%, 4.0%, 4.5% and 3.8% with a 28-day baseline (`CHANGE_MEASUREMENT_PRE_WINDOW_DAYS=28`, where `σ_w` is estimated). `tests/verify/test_verdict_validity.py` asserts the 28-day rates at 10% and 20% stay at or below 5.5% (4.25% and 4.0% in the test seeds) and pins the 7-day limitation at 10% (12.75% in the test seeds) as a known-limitation test. Workloads whose weekly level moves by more than 5% (strongly seasonal traffic, CO₂e on a grid with large weekly moves) should use a baseline of at least 14 days; the default length is under review.

Measurements decided by version 2.2 or earlier used a percentile moving-block bootstrap without the between-week term and the old outcome rule; they are kept unchanged with their `strategy_version`. Their verdicts, `realized` included, are not re-measured: only `not_realized` and `inconclusive` measurements can be re-measured on request (`core/optimization/lifecycle.py`, section 9).

The generator is seeded from the change, the measurement sequence and the quantity, so the same evidence always produces the same interval.

### Outcome rule

The rule is applied once, at the end of the post-window (plus one hour of grace for late samples). There is no repeated testing. A decision is only written from complete reads: when the post-window metrics or the health gates cannot be read, nothing is recorded and the next pass retries; when a Prometheus load driver fails, the decision waits up to 24 hours for it, then is made without it and lists it in `counterfactual_params.load_drivers_unavailable` (`pre` and `post`).

| Condition (on `allocated_cost`) | Outcome |
|---|---|
| A severe confounder was found | `contaminated` |
| Coverage below `CHANGE_MEASUREMENT_MIN_COVERAGE` (0.8), or no trusted cost in a window | `inconclusive` |
| Fewer than 5 complete days (120) of aligned post-window hours | `inconclusive` |
| CI lower bound > ε, with ε = `CHANGE_MEASUREMENT_EPSILON_RATIO` × mean counterfactual (2%) | `realized` |
| CI upper bound ≤ ε | `not_realized` |
| Otherwise (the interval straddles ε) | `inconclusive` |

The noise floor applies to both verdicts (MEA-09): before version 2.3 `realized` needed only a lower bound above zero, so a deterministic 0.3% drift (a price refresh, a rounding) was a verified saving. A saving whose interval is above zero but not above ε is reported with a "negligible saving" note in its reason. The change verdict is taken on `allocated_cost` alone; a component (`cost_cpu`, `cost_ram`) or CO₂e claim needs its own interval to be `realized` **and** the change to be realized, so the extra quantities never add a chance of a false claim.

`counterfactual_params` records `interval_method` (`circular_block_bootstrap_t_with_between_week`), `prior_week_cv`, and per quantity `baseline_weeks`, `between_week_cv` (σ_w over the counterfactual) and `between_week_basis` (`estimated`, `prior` or `deterministic_baseline`).

Values are **signed and never floored**: a cost increase is reported as a negative saving with its interval.

**Projection accuracy** (measured annual saving ÷ projected annual saving) is reported for each claimed quantity. A measurement reads allocated cost and CO₂e, so it is compared with the **allocated** projection (`impact.allocated_cost_annual` and the allocated CO₂e of the measured components, recorded as `counterfactual_params.projection_basis = allocated`), never with the realization-scaled billable projection (`potential_savings_cost`, `co2e_expected_annual_g`): projected ≠ allocated ≠ realized. The measurement also records `counterfactual_params.realization_factor`, the allocated-weighted realization factor of the change's projections, from which the API derives the billed saving to expect (an expectation, not a measurement). It is not a gate: a saving can be realized at 30% of its projection. It feeds the track record of the recommendation's source.

### Confounders

| Confounder | Severity |
|---|---|
| Another change on the same workload landed after the merge and before the end of the post-window | severe |
| The pod template changed again during the post-window with different requests or limits (a resources digest other than this change's), or without a resources digest on either side (`spec_change`) | severe |
| The workload was deleted and recreated during the post-window | severe |
| The workload's HPA changed after the rollout (replicas, so the allocated cost, moved without the change) | severe |
| The baseline's trusted cost and the after-window's come from different price bases, OpenCost or Kubecost allocation (`allocated`) versus list prices (`list_price`) (`price_basis_change`, COST-01): the price switch would read as a saving. Hours frozen before the basis was recorded are not compared | severe |
| The workload's own unit price of a resource (per charged unit, `price_card_change`) moved more than 20% | severe |
| The node pool's CPU or memory unit price (all workloads of the pool) moved more than 20% (`pool_price_card_change`) | severe |
| The node instance types running the workload changed on more than 50% of its pod-hours | severe |
| The node pool's hardware changed: its CPU-capacity-weighted instance-type mix moved by more than 25% (`pool_instance_type_change`) | severe |
| The node pool's mean CPU capacity changed by more than 50% (`pool_capacity_change`) | severe |
| Another change on the same workload landed inside the baseline window | moderate |
| The workload's HPA changed inside the baseline window | moderate |
| Mean replicas deviate more than 25% from the replicas predicted by the same counterfactual | moderate |
| The carbon factor (energy-weighted intensity × PUE) moved more than 10% between the windows (`intensity_shift`, MEA-03; informative: the CO₂e saving is normalised hour by hour, so it costs no confidence), or the post-window CO₂e has no energy behind it (`co2e_raw_delta`) | moderate |
| The workload's own unit price of a resource (per charged unit, `price_card_change`) moved more than 5% | moderate |
| No CPU/RAM cost components and no baseline unit prices, so the cost is measured at observed prices and a price move cannot be removed or detected (`constant_prices_unavailable`, `constant_price_basis = observed`) | moderate |
| The node pool's CPU or memory unit price moved more than 5% (`pool_price_card_change`) | moderate |
| The node instance types running the workload changed (total-variation distance above 25% of pod-hours) | moderate |
| The node pool's mean CPU capacity changed by more than 25% (the cluster autoscaler, `pool_capacity_change`) | moderate |
| A change to another workload whose pods ran in the same node pool landed during the measurement (`pool_change`) | moderate |
| The pod template changed during the post-window with the same requests and limits but another (or an unknown) image (`template_change`, MEA-08: usage may move, the allocated cost does not) | moderate |
| Nodes were added to or removed from the pool during the post-window without a capacity shift (`autoscaler_activity`) | mild |
| The pod template changed during the post-window with the same requests, limits and images: an env change, a rollout restart (`template_change`, MEA-08) | mild |
| More than 5% of the baseline energy has no post-window carbon factor at its hour of week and is valued at the time-averaged post factor (`co2e_factor_fallback`; informative, costs no confidence) | mild |
| More than 50 changes landed during the measurement, so later ones were not checked for pool membership (`pool_check_truncated`) | mild |

A severe confounder's detail is the reason of the `contaminated` outcome.

**Node-pool checks.** The workload's pools are the `node_pool` of the nodes its pods ran on during the post-window. The node snapshots (SCD2) are sampled every 6 hours over both windows; samples without any node of the pools (before the snapshots began) are ignored. A change to another workload counts when it completed between the merge and the end of the post-window and its pods ran on one of the pools' nodes in the two hours after its rollout. Allocated cost is requests × unit price, so other workloads' changes and autoscaling only move the idle share of CO₂e allocated to this workload (moderate), while new hardware in the pool changes its unit prices and power profile (severe). When none of the workload's nodes carries a pool label, only the price-card control runs, over every other pod of the nodes the workload ran on (`pool_price_card_change` with `evidence.scope = workload_nodes`, MEA-02); the hardware, capacity and neighbour-change checks are skipped. A failed read of the node snapshots or of the changes delays the decision to the next pass.

**Workload price card (MEA-02).** `price_card_change` compares the workload's own unit price of each resource, trusted CPU (RAM) cost over charged core-hours (GiB-hours), between the windows. A price per charged unit stays a price when the change resized the resource, so every resource is checked, including when CPU and memory were both resized. The saving itself is already measured at the baseline prices (section 3): the finding says that the observed cost moved for another reason, and above 20% that the measurement window is too disturbed to trust (contaminated). Snapshots without charged quantities use the price per requested unit; CPU is then checked only when its mean usage stayed at or below the request in both windows or its request was not resized (memory usage is not in those buckets, so a resized memory request is checked as it is).

**Pool price card.** At each pool sample the metrics of every pod are read for one hour, and the CPU (per core-hour) and memory (per GiB-hour) unit prices of the pods that ran on the pools' nodes are computed from trusted cost with CPU/RAM components, for each window. The measured workload's own pods are left out: an allocator that charges `max(request, usage)` moves the cost-per-request ratio of a workload resized below its usage although no price changed. A unit price belongs to the nodes, not to the requests, so this control works even when the change resized both resources of the workload. A pool-wide finding replaces the workload-level finding of the same resource, so a price change is never penalized twice.

**Confidence** starts at the coverage and loses 0.15 per moderate confounder, 0.05 per mild one and 0.10 when the counterfactual has no load driver or only the CPU-usage driver; it is 0 when the measurement is contaminated.

## 7. Health

The same per-replica health gates as the interim verifier apply to the change's recommendations, grouped by container: per-pod p95 usage under the applied request × headroom, restarts, OOM kills, readiness and CPU throttling. A signal that cannot be read is reported `not_available`, never counted as a pass.

They are evaluated twice:

- once the interim health window has elapsed, so a harmful change is flagged within `VERIFICATION_WINDOW_HOURS` instead of at the end of the post-window. A failure sends every awaiting recommendation of the change to `rollback_review`. When the metrics cannot be read, the check is not recorded and is retried on the next pass;
- at the decision, over the whole post-window. The gates are stored in the measurement.

**Compared with the baseline (MEA-07).** The thresholds were designed for the 72-hour interim verifier; applied as absolute levels to a 7-day window, one unrelated restart of any replica, or CPU throttling that existed before the change, sent a realized change to `rollback_review`. The baseline snapshot therefore freezes the same signals over the baseline window, per container (`BaselineSnapshot.health`: restarts, OOM kills, readiness, throttling, and the window's replica-hours), and the restart, readiness and throttling gates fail only on a worsening:

| Gate | Fails when |
|---|---|
| `restarts` | the post-window count is improbably high for the baseline rate per replica-hour — exact conditional binomial test: if the rate is unchanged, the post-window share of all restarts is binomial with the post-window share of the replica-hours, one-sided p ≤ 0.05 — **and** exceeds the expected count by at least `max(1, VERIFICATION_MAX_RESTART_DELTA)`. The tolerance scales with replica-hours. |
| `cpu_throttling` | the ratio is above the baseline ratio + `VERIFICATION_MAX_THROTTLE_RATIO` (absolute). |
| `readiness` | the ratio is below `min(VERIFICATION_MIN_READINESS, baseline − 0.01)`. |

Each compared gate records `value` and `baseline_value`. Post-window replica-hours come from the post-window hours; the interim check, and baselines without replica counts, assume the baseline's replica count. A snapshot frozen before this check (or a signal not read in the baseline) keeps the absolute rule and the gate detail says `baseline_missing`. The usage and OOM-kill gates are unchanged (a request decrease must never hide an OOM kill).

Edge cases:

- **Short baseline.** The restart test needs baseline replica-hours of at least a quarter of the post-window replica-hours. Below that, the post-window share of the exposure tends to 1 and no rise can be significant (with a 1-hour baseline, 100 post-window restarts passed), so the gate keeps the absolute rule and its detail says `baseline_too_short`. This applies to accelerated windows when the post-window is more than four times the baseline.
- **Memory increases.** When a memory increase is judged on its OOM-kill rate (section 7, reliability increases), its post-window OOM restarts leave the restart gate; the baseline snapshot also freezes each container's OOM restarts (`oom_restarts`), and the same containers' baseline OOM restarts leave the baseline count, so both sides count the same restarts. A snapshot without that value keeps the absolute rule for the restart gate, labelled `baseline_oom_restarts_missing`.
- **Throttling and readiness.** These ratios are compared as they are, with no minimum baseline length, so a short baseline gives a noisy reference. A workload already throttled or unready before the change may stay so: a baseline throttling ratio of 40% tolerates 45% after, a baseline readiness of 90% tolerates 89%. The gates judge whether the change made things worse, not whether the workload is healthy. With a clean baseline both reduce to the absolute rule.

A health failure does not change the measurement outcome: the saving is still evidence about the change. It changes what happens to the recommendations.

### Reliability increases (H1)

A request increase is a reliability fix: its cost is measured like any request change (the estimates are negative savings, reported as a cost), and its success is whether the **OOM-kill rate dropped**.

- **Baseline:** the OOM kills the recommendation observed over its evidence window (`evidence.oom_events`) of the memory-request increases, summed over the containers whose memory request was raised, divided by the time the **workload** was observed before the change, not by the whole evidence window. The evidence window starts at the cluster's data start: a workload created 40 minutes before the scan, on a cluster with 8.4 hours of data, was never exposed for the hours before it, and dividing its kills by 8.4 hours would make its baseline rate about 12 times too low (leaning the verdict towards `inconclusive`).
  - **Exposure:** from `evidence.first_observed_at` (the target's first sample inside the evidence window) to `evidence.observation_window_end`, bounded by `evidence.observation_window_seconds`. The scan records `first_observed_at` from the target's usage summary: the first sample lies in its first observed hour, and the observed collection steps (`step_count` × the query step, counted back from the window end) place it within that hour, never outside it, so collection gaps or compressed rows that overcount steps shift it by less than an hour. Without a usage summary, the first raw sample of the target's series is used. It is never earlier than the window start.
  - **Fallback:** evidence stored before `first_observed_at` was recorded, or without a usable value, keeps the whole evidence window (the previous behaviour).
  - The source of the exposure is recorded as `baseline_exposure_source` in `counterfactual_params.reliability`: `workload_first_observed` or `evidence_window` (fallback). With several raised containers, the longest exposure (and its source) is used.
- **After:** the OOM kills over the post-change window (interim window, then the whole post-window), counted in the unit of the baseline: container restarts whose termination, at the 5-minute step of the restart, was `OOMKilled`, summed over pods (`WorkloadHealthObservation.oom_restart_count`). The `oom_kills` gate itself counts pods with a kill, so a pod crash-looping on OOM would look like one kill: it is never used for the rate. When the OOM restart count cannot be read, the outcome is `inconclusive` and the strict gates stay.
- **Test:** if the rate had not changed, the post-window share of all kills would follow a binomial law with the post-window share of the observed time. The drop is `realized` when the post-window count is improbably low (one-sided p ≤ 0.10), `not_realized` when the post-window rate is not lower, and `inconclusive` with too few kills or unknown counts. An increase made without OOM history (p99 close to the request) is `inconclusive` on this test and judged by its usage gates.
- **Gate:** for a container whose **memory** request was raised with OOM history, that container's `oom_kills` gate compares the rates instead of failing on any kill: a kill after an OOM-driven increase does not send it to `rollback_review` (rolling it back would bring the kills back) unless the rate did not drop. Every OOM kill also restarts its container, so those OOM restarts are left out of the `restarts` gate (restart counters are read per pod, so they leave the `restarts` gate of every container of the change); any other restart still counts against `verification.maxRestartDelta`. The rate gate is applied per container: every other container of the same change (a decrease, a CPU-only increase, which cannot cure OOM kills, or a container with a memory decrease) keeps the strict gate, so one container's increase never hides another container's OOM kills.
- The outcome is stored in `counterfactual_params.reliability` (metric, outcome, reason, counts, hours, rates per day, p-value, baseline exposure source) and added to the measurement's reasons.
- **Objective (MEA-14, strategy 2.5).** Every change records `counterfactual_params.objective`. When **every** member raises a request, the objective is `reliability` and the change outcome is the reliability outcome above (`realized` only when the health gates pass too, `inconclusive` when the rate dropped but a gate failed; a contaminated measurement stays contaminated), not the cost outcome, which an increase always fails. The cost is reported as `cost_of_fix_annual` (positive: what the fix costs per year) and kept, signed, in the estimates; the recommendations' cost and CO₂e estimates are `not_claimed`, so a confirmed fix is `verified` with a measured saving of 0, and a fix whose kill rate did not drop is `not_realized` (its `oom_kills` gate sends the recommendation to `rollback_review`). A mixed change (a decrease and an increase) keeps the `savings` objective. The cost of a fix is not yet booked in the ledger as a negative entry, and the API and UI do not yet show it apart.

## 8. One measurement per change (C5)

A change is measured once, on its workload. The saving is split between its recommendations:

- **by cost component** when the workload's rows carry the CPU/RAM split: CPU recommendations share the `cost_cpu` saving and memory recommendations the `cost_ram` saving, each in proportion to the request reduction it made. A recommendation claims its component share only when that component's own interval shows a saving: in a `realized` change, a recommendation whose component was `not_realized` (for example memory requests that grew) or `inconclusive` gets that outcome instead of `verified`;
- otherwise **by projected share** of the `allocated_cost` saving: each recommendation's projected *allocated* annual saving (`impact.allocated_cost_annual`, `potential_savings_cost` for projections stored before the Impact Model) over the group's total, a projected increase weighing nothing (equal shares when nothing was projected).

**Component claims never exceed the net saving.** A bundle can cut CPU (`cost_cpu` −$100/yr) while it raises memory (`cost_ram` +$80/yr), or a component the change did not touch can grow. The component shares that save are scaled by `net ÷ (sum of the saving components)`, with `net` the change's measured `allocated_cost` saving, whenever the components add up to more than the net (and to zero when the change saved nothing net). The bundle above books the net $20/yr on the CPU recommendation, never the gross $100/yr; the memory recommendation keeps its signed, unclaimed estimate (`not_realized`, no accrual). Components that add up to at most the net are not scaled.

Shares within a basis sum to one, so a change is never claimed twice. Each recommendation receives one immutable row in `savings_measurements` (`change_id`, `group_id` = the change measurement), with its share of the estimates and the change's outcome. Its status follows:

| Change outcome | Recommendation |
|---|---|
| `realized` | `verified`; the ledger accrues its measured share (method `measured`). |
| `not_realized` | `applied` with `verification_status=failed`; signed measured values are kept. |
| `inconclusive`, `contaminated` | `applied` with `verification_status=inconclusive` (reasons prefixed `contaminated:` for a contaminated change). |
| a health gate failed | `rollback_review`. |

A recommendation that joins a change after it was measured gets an `inconclusive` row: it was not part of the split. A realized change is measured once, so a re-measurement requested by one of its recommendations does not start a new measurement: the recommendation gets a new row with the existing decision and the reason `re-measurement not started: change … is realized and is measured once`.

## 9. Lifecycle (C2)

```
applied → measuring → realized | not_realized | inconclusive | contaminated
realized → regressed | closed
not_realized | inconclusive | contaminated → measuring   (explicit re-measurement only)
```

The repository rejects any other transition. The two self-transitions are `measuring → measuring` (used for `health_checked`) and `closed → closed`, which ends the measured accrual of a superseded change (`superseded_ended`, or `workload_deleted`; see [section 10](#10-drift-monitor-c8)). Each transition is a compare-and-swap on the stored state and version, written in the same transaction as its event (`change_recorded`, `measurement_started`, `health_checked`, `measurement_decided`, `remeasure_started`, `superseded`, `regressed`, `spec_drift`, `workload_recreated`). `savings_reversed` and `template_change` (MEA-08: a template change with the change's requests and limits) are recorded without a state change. A re-measurement (`POST /api/v1/recommendations/{id}/remeasure` on any of the change's recommendations) starts a new post-window at the next hour and a new measurement that supersedes the previous one; the baseline stays the frozen snapshot. A newer change on the same workload closes a realized change that landed before it (`superseded`, with `details.superseded_by`; a change recorded late, such as an adopted one, never closes a change that landed after it); the superseded change keeps accruing its own measured step and stays watched by the drift monitor.

A decision persisted before a crash is replayed: a change measurement and each recommendation's row are unique per measurement cycle, so a second pass reuses them instead of measuring again.

## 10. Drift monitor (C8)

The `savings-drift` controller loop (hourly, leader only, `greenkube.verify.drift`) watches every `realized` change.

**Drift.** The saving of a request rightsizing is the allocated cost freed per replica, so the monitor compares the workload's daily allocated cost **per replica-hour** with the baseline snapshot (`B`) and with the measured post-window (`A`):

```
lost_share(day) = (rate(day) − A) / (B − A)
```

All three windows are valued at the constant baseline prices the saving was measured at (section 3: the snapshot's `price_card`, on the charged quantities; `constant_price_basis` is recorded in the payload), so a later price rise does not reverse a saving claimed at constant prices. Per-replica rates do not move with load-driven replica counts or prices; they move when the requests creep back (a VPA in auto mode, an admission webhook, a LimitRange) or the charged usage grows above the request. Only complete UTC days after the post-window with at least 18 hours of trusted cost count, over the last 7 days. When `lost_share ≥ CHANGE_DRIFT_THRESHOLD` (0.5) on each of the last `CHANGE_DRIFT_SUSTAINED_DAYS` (3) consecutive days, the change becomes `regressed` (event `regressed`, actor `drift-monitor`, payload: `B`, `A`, threshold, onset and the daily lost shares) and its `verified` recommendations become `regressed`, which stops their accrual and counts against their source's track record. A post-window without a per-replica saving is not monitored.

**Spec drift.** The usage drift is assessed first, so a revert in git whose usage has already drifted for the sustained period is a regression. Otherwise, when the latest spec observation after the rollout has a pod-template digest other than the change's `spec_digest_after`, or another workload UID, **and its resources digest differs from the change's** (the requests were reverted or changed), the change is closed (`realized → closed`, event `spec_drift` or `workload_recreated`): its measured saving no longer describes what runs. A template change or a recreated workload with the change's requests and limits (an image deployment, an env change, a rollout restart) closes nothing: the change stays realized, keeps accruing, and the monitor records an informational `template_change` event once per template revision (MEA-08). For a change or an observation stored without a resources digest (before migration 0136) the monitor reads the live container requests of the workload before closing: if every member's applied request still runs, nothing closes (`template_change` with `resources_source = live_requests`); if they differ, or cannot be read, the change is closed as before, and the event reason says which. Every container counts: with the per-container requests recorded on the change (`details.container_requests`, taken from the detector's or the live workload snapshot) the whole live map must match; without them a live container the change never recorded makes the comparison unknown, and the change closes. A change recorded without a workload snapshot (`PATCH /apply` and adopted changes read the live workload when they are recorded; when that read fails they have no pod-template digest) is compared with its live requests on every pass: requests that differ from the applied ones close it with event `spec_drift`. Its `verified` recommendations become `regressed` as well, so their measured accrual stops from the first observation of the differing run (`accrual_end` in the event payload). The monitor acts two hours after the observation, and a newer recorded GreenKube change on the workload closes the change as `superseded` instead; each change then keeps accruing its own measured step.

**Deletion.** The monitor asks the Kubernetes API whether a realized change's Deployment, StatefulSet or DaemonSet still exists. HTTP 404 records a `workload_absent` event; when the workload is still absent two hours later the change is closed (`realized → closed`, event `workload_deleted`, `accrual_end` = the first absent observation) and its `verified` recommendations become `regressed`, so their measured accrual stops there. A workload found again in between records `workload_present` and nothing closes; any other API answer (no client, forbidden, timeout) decides nothing.

**Superseded changes.** A change closed as `superseded` keeps accruing its own measured step: the newer change is measured against a baseline frozen after the earlier change (its 7 days before the merge), so the two steps add up and nothing is counted twice. A change whose newer change lands inside its baseline window has a `change_in_baseline` confounder. The superseded change is never left unwatched; on each pass the monitor:

1. ends its accrual when any newer change on the workload has ended (`regressed`, or closed by a spec drift, a revert, a recreation or a deletion): event `superseded_ended` (`closed → closed`), `accrual_end` = the earliest `accrual_end` of those changes. This fails closed: when the newest step is lost, the monitor cannot tell whether the earlier step still holds, so neither is credited any more until a new change is measured;
2. otherwise, when the newest change is `realized`, does nothing more: that change's own watch covers the workload and ends it through rule 1;
3. otherwise (the newest change is still measured, or was not realized, inconclusive or contaminated, so nobody else watches the workload) runs the **deletion** check on the superseded change itself (event `workload_deleted`, `closed → closed`) and the **spec drift** check against the newest change's template (`spec_digest_after`) and workload UID (event `superseded_ended`).

In every case the change's `verified` recommendations become `regressed` and what accrued after `accrual_end` is reversed like any other ending (below). Changes closed as superseded before this rule existed are recognized by their closing `superseded` event.

**Reversal entries.** The ending paths store where the measured saving ended (`details.accrual_end` on the change: the drift onset, which is the first day of the sustained run, or the first differing spec observation). The measured accruals written after it, or after the verification time if that is later, are reversed: one signed ledger row per recommendation, method `measured`, covering `[accrual end, end of the last accrued slot)`. Its amount is the negative sum of the measured accruals actually stored in that interval (pro rata for a slot that straddles its start), so slots that were never accrued are not reversed and the interval nets to exactly zero (LED-12). The row is marked `row_kind = 'drift_reversal'`. It is written two hours after the state change, once an accrual run in flight has finished, and the change records a `savings_reversed` event listing the rows. A later pass reverses only what no earlier `savings_reversed` entry covers, so an accrual written late gets an adjacent entry, never an overlapping one. A reversal within one accrual slot widens its period label by one second so it cannot take that slot's idempotency key; its amount uses the exact period. Ended changes are checked for 14 days after their state change. In the savings ledger v2 each reversal row becomes a `reversal` entry with reason `drift`, linked to the first measured accrual it cancels ([section 12](#12-savings-ledger-v2-c6)). The ledger counters report reversals as reversed (`greenkube_cost_savings_reversed_dollars_total`, `greenkube_co2e_savings_reversed_grams_total`); savings accrued before the accrual end are kept.

## 11. Auditing a measurement

1. `GET /api/v2/changes/{id}` returns the change, its state history and its baseline snapshot metadata. `baseline.content_verified` must be `true`.
2. `GET /api/v2/changes/{id}/measurements` returns each decided measurement with its windows, load driver, `counterfactual_params`, per-quantity estimates and intervals, confounders, confidence, health gates, `allocations` and the per-recommendation rows.
3. `evidence_sha256` covers every decided field of the measurement and `baseline_sha256` the snapshot it used. Recomputing the counterfactual from the snapshot's `hours` and `load_series`, the post-window rows and the parameters above must give the same estimates; the bootstrap seed is derived from `change_id`, `sequence` and the quantity.
4. Database triggers reject `UPDATE` and `DELETE` on `change_events`, `change_members`, `baseline_snapshots`, `change_measurements`, `change_state_events`, `savings_measurements` and `savings_ledger_entries`.
5. `GET /api/v2/ledger/entries?change_id={id}` lists the ledger entries of the change; `GET /api/v2/ledger/summary` reports the last hash-chain verification.

## 12. Savings ledger v2 (C6)

Every saving GreenKube reports ends up as an **entry** of an append-only, hash-chained ledger (`savings_ledger_entries`, `greenkube.verify.ledger`). An entry is one signed amount of one quantity earned during one period under one method:

| Column | Meaning |
|---|---|
| `entry_kind` | `accrual` (an amount earned), `reversal` (cancels `reverses_entry_id`), `restatement` (replaces the projected accrual `restates_entry_id` with the measured amount of the same period). |
| `book` | `accrued` mirrors the v1 staging ledger (`accrued_only_*` in `GET /api/v1/recommendations/savings`); `restatement` holds the restatements and the reversals of the projections they replace. |
| `reason` | `accrual`, `drift` (a drift-monitor reversal, [section 10](#10-drift-monitor-c8)), `supersession` (rollback review, revert or phantom repair), `restatement`. |
| `method` | `projected`, `measured_allocated` (this methodology, allocated cost), `realized_billed` (pool-level realization, C10, not written yet), `user_declared`. Never summed together. |
| `basis` | The accounting basis of the amount (LED-01): `allocated` (what the workload is charged by the Impact Model's allocation; projected and measured amounts since `ledger/2`), `billable_expected` (allocated × realization factor; projected entries stored before `ledger/2`, and projections of recommendations without an Impact Model projection), `billed` (`realized_billed`), `declared` (`user_declared`). Entries stored before migration 0160 have no stored basis (their hash is unchanged); the API, the summary (`accounting_bases`) and the exports (`basis`, `x-greenkube-basis`) report the basis their method had then. |
| `annual_rate` | The annual rate the accrual was computed from (LED-11): `value = annual_rate × (period_end − period_start) / 31,557,600 s`. Set on accruals written since `ledger/3` (migration 0293), part of their hash payload; the v1 row also keeps the currency and, for a measured row, the measurement whose rate it used, read at accrual time (so a later re-measurement does not change which measurement an entry names). Restatements carry the measured rate they were computed from; entries stored before, reversals and the slot restatements of uncovered parts have none. `price_card_version`, `intensity_g_per_kwh` and `intensity_source` are still not filled. |
| `quantity`, `value`, `unit` | `cpu_core_h` (core-hours) and `mem_gib_h` (GiB-hours) for released capacity, never money; `cost` in the currency its recommendation was priced in (the projection's `impact.currency`; `IMPACT_PRICING_CURRENCY` when the recommendation has none), so a later currency change never relabels past accruals, or `co2e_g` in gCO₂e. Values are signed and never floored. The summary keeps one total per method, quantity and unit: amounts in different currencies are never added. |
| `period_start`, `period_end`, `slot_start` | The accrued period, on the fixed UTC hour grid of the accrual job. |
| `recommendation_ids`, `change_id`, `measurement_id`, `pr_url`, `method_version` | Provenance: the change's recommendations, the change and its pull request, the measurement and the strategy version (`request_rightsizing/2.0`) of measured amounts. |
| `cluster_uid`, `cluster_name` | The UID of the `kube-system` namespace (roadmap N9), stored next to `CLUSTER_NAME` in `cluster_identities` the first time it is read and never replaced; `name:<CLUSTER_NAME>` without Kubernetes access. Signal ids and recommendation fingerprints keep their own cluster key. |
| `seq`, `prev_hash`, `hash` | The entry's position in its cluster's chain and the chain link. |

**Append-only.** Database triggers reject `UPDATE` and `DELETE` (and `TRUNCATE` on PostgreSQL). A correction is always a new entry.

**Totals and growth (LED-09).** `savings_ledger_totals` keeps, per cluster and per (namespace, recommendation type, method, quantity, unit, book, entry kind, basis, cost-of-fix group), the signed sum, the sums of the positive and of the negative entries and the entry count. It is updated in the transaction that appends the entries, so the all-time summary, the savings report, the lifetime counters and the accrued-book reconciliation read a few rows instead of every entry; the reconciliation with the v1 ledger checks it every `ledger-chain` tick, and since the totals are not chained, every full verification re-derives them from the chained entries and fails with `totals_mismatch` when they differ. Windowed reads still prorate the entries of the window. The ledger still grows by one v1 row and up to two v2 entries per accruing recommendation, method and hour (about 8.8 million v1 rows and 17.5 million entries a year for 1,000 accruing recommendations); a daily grain, partitioning, segmented verification and archival are not implemented yet.

**What the chain guarantees (LED-05).** The chain detects an accidental or partial change: a modified, removed or reordered entry, or a lost tail, fails verification. With `LEDGER_CHAIN_KEY` (a Kubernetes Secret generated once by the chart's credentials bootstrap Job, never stored in the database) new entries are chained with HMAC-SHA256 and carry `chain_key_id`, a public fingerprint of the key: someone who can write to the database but does not hold the key cannot recompute them, so multiplying values and re-chaining fails with `hash_mismatch`. An entry without the key after a keyed one fails too (`hash_mismatch`); a keyed entry fails without the key (`chain_key_missing`) or with another key (`chain_key_mismatch`). Never rotate or lose the key: entries chained with it only verify with it. Entries written before the key existed keep the plain sha256 rule and stay valid, but they remain recomputable by a database writer, and so does a whole chain re-written without the key: `greenkube_ledger_chain_head_keyed` (1 when the verified head is keyed) and `greenkube_ledger_chain_head_seq` in Prometheus are the witnesses of such a rewrite, provided Prometheus kept the earlier values. The triggers still belong to the GreenKube database role, which can disable them, and the verified head is stored in the same database: a checkpoint outside the database and a database role that does not own the table are not implemented yet.

**Hash chain.** Each cluster's entries are numbered without gaps (`seq`) and chained: `hash = sha256(prev_hash || canonical_json(entry))`, where the canonical JSON covers every column except `hash` and `prev_hash` (sorted keys, timestamps as `YYYY-MM-DDTHH:MM:SS.ffffffZ`, floats as their shortest exact representation). Appends are serialized per cluster (an immediate transaction on SQLite, a transaction-scoped advisory lock on PostgreSQL), and every entry has a deterministic `entry_key`, so retries and concurrent writers never fork the chain or duplicate an entry.

**Verification.** The controller's `ledger-chain` loop (leader only, every `LEDGER_CHAIN_VERIFY_INTERVAL`, default 1 hour, and at start) walks each chain: positions must follow each other, every `prev_hash` must be the previous `hash`, every `hash` must match its recomputed value, every `entry_id` its key and cluster, and every reversal must cancel its target exactly (opposite value, same quantity and unit, `reversal_mismatch`; drift reversals, which cancel a period, excepted). Each verified head is published as `greenkube_ledger_chain_head_seq{cluster_uid}` and `greenkube_ledger_chain_head_info{cluster_uid,head_seq,head_hash}`, so the Prometheus history is a witness kept outside the database. It verifies incrementally from the last verified head and the whole chain once a day; a chain shorter than the head it verified before, or with another hash there, lost its tail. Failures increment `greenkube_ledger_chain_verification_failures_total{reason}` (`missing_entry`, `broken_link`, `hash_mismatch`, `identity_mismatch`, `truncated`, `head_rewritten`), set `greenkube_ledger_chain_ok{cluster_uid}` to 0 (the `GreenKubeLedgerChainVerificationFailed` alert of the chart's PrometheusRule fires on it, so a failure found by a pod's first pass alerts too, for as long as the chain stays broken), and are reported by `GET /api/v2/ledger/summary` (`chain`).

A failure is sticky. `ledger_chain_status` keeps the last head that passed (`verified_head_seq`) as the anchor of every later verification, so a lost tail keeps failing, also once new entries reuse its positions (`head_rewritten`). After the incident is investigated and the chain is restored or accepted, an operator accepts the current head with `greenkube db ledger-accept-head --cluster-uid <uid> --reason "..."` (LED-05): the chain must still pass the structural checks, nothing is written to the ledger, and the acceptance is logged with the reason and the head it replaces. This replaces deleting the cluster's `ledger_chain_status` row, which still works but leaves no record. After a backup restore or a failover that lost the last entries, the stored anchor (and the head published in Prometheus) is ahead of the chain until this acceptance.

**Single read model (LED-04).** Every user-facing savings number is read from the entries: the `*_to_date` blocks of `GET /api/v1/recommendations/savings` (and so the overview hero) are the restated totals of each method over the window (`source: ledger_v2`, with the accrued book alone in `accrued_only_*`), the `greenkube_*_savings_attributed_*` counters sum the positive entries and the `greenkube_*_savings_reversed_*` counters the negative ones (supersession, drift and restatement reversals), and the `greenkube_dashboard_savings_*` window gauges are the restated totals too. Before the ledger has a cluster identity (first start, no controller yet), the report and the gauges read the v1 table and say so (`source: ledger_v1`, diagnostic `ledger_v1_fallback`).

**Dual write.** The savings attribution job writes the v1 ledger (`recommendation_savings_ledger`), a write-ahead staging table that is no longer a reporting source. Its rows are append-only (migration 0161: triggers reject `DELETE` and every `UPDATE` except setting `superseded` from false to true). On every `ledger-chain` tick the accrued book of each method and quantity must equal the non-superseded v1 rows (relative 1e-9): `greenkube_ledger_reconciliation_ok{cluster_uid}`, alerted after 3 hours by `GreenKubeLedgerReconciliationFailed`. Each attribution run that reached the database is followed by a ledger pass, and the `ledger-chain` loop catches up whatever a failed pass left (`greenkube_ledger_write_errors_total`). A pass:

1. projects every v1 row after its watermark (`ledger_projection_watermarks`, advanced in the same transaction) into one entry per non-zero quantity. v1 `measured` becomes `measured_allocated`. A v1 drift reversal (`row_kind = 'drift_reversal'`, whatever the signs of its quantities; for rows stored before migration 0291, an off-grid negative `measured` row) becomes a `reversal` with reason `drift`. Legacy compressed hourly rows are projected too. Rows are selected by an anti-join (v1 rows with a non-zero quantity and no entry yet), never by id alone: the attribution job and the drift monitor write in separate transactions, so a v1 id can commit long after higher ids were projected. A pass reads from 1,000 ids below the watermark; a full sweep from the first id runs at least once an hour per writer and on every `ledger-chain` tick, so a late row is projected at the latest on the next tick (`greenkube_ledger_late_rows_projected_total`). What a full sweep still finds unprojected (an invalid row, a backlog above the per-pass cap) is reported by `greenkube_ledger_unprojected_rows{source_table}` and alerted after 3 hours by `GreenKubeLedgerProjectionBacklog`;
2. supersedes, on every pass, the v1 rows of every recommendation in `rollback_review`, `reverted`, `failed` or `stale` that are still live (the one-shot call of the lifecycle loop is only a fast path: a failed call, or an accrual written after it, is caught up by the next pass, LED-08), then reverses (reason `supersession`) every entry whose v1 row is flagged `superseded`, the restatement and refutation entries attached to it, and the slot restatements and reinstatements of those recommendations;
3. restates (BUG-39): for each `verified` (or later `regressed`) recommendation, every projected accrual that ended at or before `verified_at` and is not reversed yet gets a `reversal` and a `restatement` at the measured annual rate over the same period (`measured_cost_saved`, `measured_co2e_saved_grams`), linked to the projection, the measurement and the change. Every hour slot of `[applied_at, verified_at)` that no projected or measured accrual of the quantity covers (a projection of exactly 0, slots before the accrual job saw the change) gets a `restatement` at the measured rate for its uncovered part (`entry_key` `restatement:slot:{recommendation}:{slot}:{quantity}`), so the measured saving of the whole measurement window is booked.

4. refutes (LED-03): for each `not_realized` recommendation (status `applied`, verification `failed`) every unreversed projected accrual is reversed (reason `not_realized`, `restatement` book). When the measurement found a loss (a negative annual rate: the change costs more) the projection is restated at that rate instead, and the uncovered slots up to the end of the measurement window are booked at it, so the loss reaches `measured_allocated`. A positive rate the measurement could not claim is never booked;
5. reinstates (LED-08): when a recommendation accrues again after a supersession (a dismissed rollback review), each supersession reversal is cancelled by a `reversal` with reason `reinstatement` in the `restatement` book (the v1 flag cannot be unset, so the `accrued` book keeps mirroring v1), and the restated total re-credits the accruals written before the review.

6. books what the change measurement found besides the saving, for each `verified` recommendation, per hour slot from `applied_at` to the last complete slot, in the `restatement` book (they come from the measurement, not from the v1 staging ledger): the **released capacity** (quantities `cpu_core_h` in core-hours and `mem_gib_h` in GiB-hours, reason `released_capacity`): the request effect the measurement booked (`capacity.total`, signed: an increase reserves capacity) times the recommendation's allocation share, a CPU change releasing no memory of its own and the reverse. Released capacity is never converted to money and never part of a savings total (the savings report, the counters and the FOCUS export leave it out; the summary and the CSV export list it under its own quantity). The **cost of a reliability fix** (`cost_of_fix_annual` of a request increase, MEA-14) is booked as a negative `cost` entry under `measured_allocated` with reason `cost_of_fix`: what the fix costs, never a saving. It is never netted into a savings total: the savings report shows it in `reliability_cost_to_date`, the ledger summary in `cost_of_fix`, and the savings counters and dashboard windows leave it out.

Every step is derived from the recommendation state and idempotent, so the first pass after an upgrade corrects the entries written before.

**Inconclusive verdicts.** The projections accrued before an `inconclusive` verdict are kept, never confirmed: `GET /api/v1/recommendations/savings` reports them in `projected_unverified_to_date` and leaves them out of `projected_to_date`.

**One basis (LED-01).** Since `ledger/2` the attribution job accrues a projection on the **allocated** basis, the basis a change measurement compares with: the Impact Model's `allocated_cost_annual` and the allocated CO₂e of the components a measurement sees (operational energy and idle share). Projected and `measured_allocated` amounts are then the same quantity before and after measurement, and a restatement is like for like. The realization factor is never applied to an accrual: the billable expectation (allocated × realization factor) is a derived figure, reported apart in the savings report (`realization.projected_billable_cost_annual_expected`). A recommendation stored without an Impact Model projection accrues its legacy projected value under basis `billable_expected`.

**Restatement limits.** A projection is restated at the measured annual rate of the recommendation's latest measurement (the `measurement_id` of the restatement names it). A later re-measurement restates it again: the restatement from the earlier measurement is reversed and replaced at the new measured rate (`entry_key` suffixed with the new `measurement_id`), and a projection refuted by an earlier `not_realized` verdict gets the measured amount of its period once a re-measurement verifies the change. A projection reinstated after a dismissed review is not restated or refuted again by a later measurement, and a second review of the same recommendation does not reverse what an earlier reinstatement re-credited before it.

**Reading the books.** The `accrued` total of a method equals the v1 ledger of that method (all time, or prorated over a window exactly as the savings report does). The `restated` total (both books) is the best current statement and the figure every user-facing number shows (LED-04): after a measurement, the projection of the measured period has moved to `measured_allocated`. A recommendation superseded after a restatement ends at zero in both books.

**Rollups** are read-side: the `savings_ledger_daily_rollup` view sums entries per UTC day, namespace, method, quantity, book and kind. Nothing is ever compressed or deleted.

**Export.** `GET /api/v2/ledger/export` streams the entries as CSV (one row per entry, with `window_share` and `window_value` for a window) or, with `format=focus`, as FOCUS-aligned rows (one per accrual group, cost and CO₂e together): `ChargeCategory` `Credit` for accruals and `Adjustment` (`ChargeClass` `Correction`) for reversals and restatements, `EffectiveCost` = −saving (avoided spend), `BilledCost` 0 except for `realized_billed`, and the `x-greenkube-*` extension columns (`method`, `measurement-id`, `pr-url`, `co2e-g`, `saving`, `book`, `hash`, …). The sum of `x-greenkube-saving` over `accrued` rows of a method reconciles with the savings report. A window needs both bounds (`start` and `end`, or `last`), as in the savings report. String cells are guarded against spreadsheet formula injection like the v1 CSV report (a leading `=`, `+`, `-` or `@` is prefixed with `'`; numeric columns are written as numbers), and `pr-url` is the web URL users open. The extension column names follow the roadmap (`x-greenkube-*`); FOCUS 1.0 prescribes an `x_` prefix for custom columns, so a FOCUS validator flags them until the names are aligned.

## Limitations

- **Request changes and asset deletions only.** `request_rightsizing` and `resource_deletion` are the only strategies. Replica, schedule and node-pool changes need their own strategies.
- **Allocated, not billed.** The measured saving is allocated cost. The bill only drops when nodes are removed; pool-level realization (C10) is not implemented.
- **Pool confounders need pool labels.** The node-pool hardware, capacity and neighbour-change checks use the `node_pool` of the node snapshots; clusters whose nodes carry no pool label get only the price control over the workload's nodes. The saving is measured at the baseline prices either way (MEA-02).
- **Drift is per replica.** The drift monitor watches allocated cost per replica-hour, the quantity a request change moves; a regression that only shows in replica counts (an HPA retuned) is not a drift of this change, and CO₂e is not monitored on its own.
- **Reversals are whole.** A regression reverses the full measured rate from the onset, even when only part of the saving was lost (for example 60%). This is conservative: the remaining part is not credited until a new change is measured.
- **Deletion and supersession.** A deletion ends the measured accrual at the first absent observation, up to one monitor interval (1 hour) after the actual deletion; the accruals of that hour are kept. A change superseded by a newer recorded change is closed, but its recommendations keep accruing their measured step next to the new change's until a newer change ends or the workload is deleted or drifts; the earlier step is then ended too, even when only the newer step was lost (conservative).
- **A superseded change under a newer change that is not realized.** While the newest change on the workload is not realized (`not_realized`, `inconclusive`, closed), a superseded change is watched for deletion and for a pod-template drift away from the newest change, not for a usage drift (its own usage-drift assessment would misfire against the newer template); a slow erosion of its saving is then only seen once a newer change is measured. A newer change that partly undoes the superseded one (a CPU cut followed by a reliability increase) and is not realized does not end the superseded change's accrual either, and its cost step is not booked: the books can then overstate the workload's saving by that increase until the newer change is measured as `realized` or `regressed`.
- **Accelerated demo windows.** `CHANGE_MEASUREMENT_ACCELERATED` (quickstart only) accepts a baseline of 1 hour or more and a post-window of 30 minutes or more, and measures on demo rules (strategy 2.5, MEA-10): the rows are bucketed into **5-minute slots** instead of UTC clock hours (rates stay per hour; coverages are shares of a slot), the counterfactual of every post slot is the **baseline mean** (`model` and `method` `flat_mean_accelerated`: no hour-of-week seasonality, no load driver, no between-week term), the interval adds the standard error of the post-slot savings and of the baseline mean (circular block bootstraps with 15-minute blocks, `interval_method = circular_block_bootstrap_t_with_baseline_mean`), and a verdict needs **6 aligned post slots** (30 minutes) instead of 5 days, with the usual coverage and noise floor. These demo thresholds (`counterfactual_params.demo_thresholds`) are never used outside the accelerated mode. Every such measurement records `representative: false` and `time_grid_seconds = 300`: a load or price move during the demo windows is attributed to the change, so the verdict shows the pipeline end to end (`/changes`, `/ledger`, drift), not a saving. Its verified recommendations carry `baseline.measurement_representative = false`: their measured saving never accrues in the savings ledger (v1 or v2, so never in the ledger summary or export) and never restates a projection. The accelerated flag must stay off in production.
- **One baseline week.** With the default windows each hour of the week has a single baseline value; the load regression then uses weekday/weekend hours of the day instead. The interval adds the assumed week-to-week variation `CHANGE_MEASUREMENT_PRIOR_WEEK_CV` (5%) instead of measuring it, so a quantity that varies more between weeks (CO₂e in a wind-heavy zone) is decided with an optimistic interval (false-`realized` rate 16% at a 10% week-to-week variation and 33.5% at 20%, against about 4% with a 28-day baseline; see the known limitation in section 6), and an unusual baseline week (a holiday, an incident) biases the counterfactual. No control group is subtracted yet (a level shift common to the cluster is not cancelled, only covered by the interval). Use a longer `CHANGE_MEASUREMENT_PRE_WINDOW_DAYS` (14 days enables hour-of-week slots) for such workloads.
- **Load-driver heuristics.** The ingress-nginx and Envoy drivers assume a Service named after the workload, and the Envoy driver assumes Contour's cluster naming. Set `greenkube.io/load-metric` when that does not hold.
- **Inconclusive reasons.** Since 2.5 the reason of a quantity without a value names the cause (MEA-10): no metric rows in the window, rows without a trusted cost or carbon value (request quantities are never called trusted), or hours present but each below the 50% coverage an hour needs (with their count and the best coverage). Each decided measurement also records `untrusted_cost_hours` and `baseline_untrusted_cost_hours` (MEA-05): the workload hours of the post-window and of the baseline window with metric rows but no trusted cost, the sum over the hours of `coverage - cost_coverage` (an hourly rollup row with one untrusted sample adds its five minutes, not the hour). They say why a cost verdict lost hours and are covered by the evidence digest; they are never a gate. Measurements decided before they were recorded keep `null`.
- **Spec observations depend on the lifecycle interval.** A spec change reverted between two detection passes is not seen.
- **Changes closed by an image deployment before MEA-08 stay closed.** Changes closed with event `spec_drift` before the resources digest existed are not re-opened automatically, even when their applied requests still run; re-opening them needs a `closed → realized` repair and a ledger restatement of their reversal entries, which are not implemented.
